0. Decision Summary

The Java service formerly called the Runtime Gateway was never really a gateway: its job is to host the Flowable engine. The platform now has a real, standalone edge gateway (nginx) outside Java, and the Java service is renamed workflow-runtime and sits behind it.

What's Decided
  • nginx is the only public entry point. It serves the SPA and routes /api/* to services. It owns CORS, rate limits, request ids and access logs.
  • nginx does not validate JWTs. Open-source nginx can't verify JWKS-signed tokens (only nginx Plus has auth_jwt). Every service verifies the Supabase JWT itself. If central checking is wanted later, add auth_request to a small token-verify endpoint.
  • Supabase stays as the identity and design-time data backend. Rebuilding it as custom services is the separate "Supabase-free" track (Database/SUPABASE_FREE_STACK_PROMPT.md), deliberately deferred.
  • Split only as far as the product needs today. New services are extracted when a concrete trigger shows up (Section 5), not up front.
  • Database per service. workflow-runtime has its own Postgres locally; it no longer needs the Supabase database password to run.

2. Edge Gateway (nginx)

Config lives in gateway/templates/cwp.conf.template (rendered by the nginx image's envsubst step at start) and gateway/snippets/cwp-api.conf (shared by every API route). The gateway image is built from the repo root: stage 1 runs npm run build in Designer/ with VITE_API_BASE_URL=/api; stage 2 is nginx serving that build.

  • CORS: the request's Origin is echoed back only when it matches the CORS_ALLOWED_ORIGINS regex (default ^http://localhost:5173$, for Vite dev). Preflight OPTIONS requests are answered by nginx with 204 and never reach a service, since they carry no Authorization header and every service would reject them with 401. Services must not set their own CORS headers; nginx hides any they send.
  • Why a snippet instead of a parent location: an if in a parent location does not run for requests matched by a nested one, so preflights would have leaked through to the services.
  • Request ids: a caller-supplied X-Request-Id is kept, otherwise nginx mints one. It is forwarded to the service, returned to the client, and written to the JSON access log.
  • Upstreams resolve per request (Docker's embedded DNS, resolver 127.0.0.11), so the gateway starts even when a service isn't running; that route returns 502 instead of nginx refusing to boot.

3. Request Flow & Auth

  1. The browser signs in with Supabase Auth directly and receives a JWT (unchanged).
  2. Design-time reads and writes go straight to Supabase PostgREST, governed by RLS (unchanged).
  3. Calls to CWP's own services go through Designer/src/lib/apiClient.ts (apiFetch), which prefixes VITE_API_BASE_URL and attaches the Supabase JWT as a Bearer token.
  4. nginx routes by path prefix and forwards the token untouched.
  5. Each service verifies the JWT against Supabase's JWKS endpoint and reads app_metadata.role and the tenant id from its claims.
