0. Decision Summary

As of November 18, 2026 the platform runs as five services behind one nginx edge gateway. The Java service that used to do everything (workflow-runtime) was split three ways: identity-service (login and tenant membership), design-service (workflows, versions, approvals, audit) and flowable-wrapper (the Flowable engine and every runtime endpoint: deploy, start, claim, complete and the rest). agentic-designer and spend-tracker are unchanged.

What's Decided
  • nginx is the only public entry point. It serves the SPA and routes /api/* to services by path prefix. It owns CORS, rate limits, request ids and access logs. It never routes /internal/**.
  • identity-service issues the login tokens (RS256) and publishes the public key at /.well-known/jwks.json. Every other service verifies tokens against it, so no service shares a signing secret. nginx does not validate tokens.
  • Role and status come from identity-service, not the token. flowable-wrapper and design-service re-check the caller on every write through /internal/identity/... and cache each answer for up to 30 seconds (IDENTITY_CACHE_TTL). A demotion or deactivation takes effect within that time. If identity-service is unreachable, writes fail with 503 rather than trusting the token.
  • One database role per service. All services share one Postgres for now, but each logs in as its own role (Database/roles.sql) and gets "permission denied" on the other services' tables. Moving to separate database servers later is a configuration change plus dropping the cross-service foreign keys.
  • One audit log, owned by design-service. Design-time entries come from Postgres triggers; identity-service posts role and status changes to design-service's /internal/design/audit inside the change's transaction, so a change that can't be audited rolls back. Entries carry actor ids only.
  • No further splitting of the engine. Every Flowable endpoint shares one engine and its ACT_* tables, so they stay in flowable-wrapper.

2. Edge Gateway (nginx)

Config lives in gateway/templates/cwp.conf.template (rendered by the nginx image's envsubst step at start) and gateway/snippets/cwp-api.conf (shared by every API route). The gateway image is built from the repo root: stage 1 runs npm run build in Designer/ with VITE_API_BASE_URL=/api; stage 2 is nginx serving that build. The Vite dev server's proxy (Designer/vite.config.ts) mirrors the same routes for local development.

RouteGoes toNotes
/SPAUnknown paths fall back to index.html for client-side routing; /assets/ is cached for a year (hashed filenames)
/healthznginx itself{"status":"ok"}
/api/identity/**identity-service /identity/**Rate limit 20 req/s per IP, burst 40
/api/design/**design-service /design/**Rate limit 20 req/s per IP, burst 40
/api/flowable/**flowable-wrapper /runtime/**Rate limit 20 req/s per IP, burst 40
/api/agent/**agentic-designer /**Rate limit 2 req/s per IP, burst 5; response buffering off for server-sent events; 300s read timeout
/api/spend/**spend-tracker /**Rate limit 20 req/s per IP, burst 40. /api/spend/events returns 404: usage ingest is internal only
any other /api/*nginxJSON 404 (including the retired /api/runtime/**)
  • CORS: the request's Origin is echoed back only when it matches the CORS_ALLOWED_ORIGINS regex (default ^http://localhost:5173$, for Vite dev). Preflight OPTIONS requests are answered by nginx with 204 and never reach a service, since they carry no Authorization header and every service would reject them with 401. Services must not set their own CORS headers; nginx hides any they send.
  • Why a snippet instead of a parent location: an if in a parent location does not run for requests matched by a nested one, so preflights would have leaked through to the services.
  • Request ids: a caller-supplied X-Request-Id is kept, otherwise nginx mints one. It is forwarded to the service, returned to the client, and written to the JSON access log.
  • Upstreams resolve per request (Docker's embedded DNS, resolver 127.0.0.11), so the gateway starts even when a service isn't running; that route returns 502 instead of nginx refusing to boot.

3. Request Flow & Auth

  1. The browser signs in with POST /api/identity/auth/login (username and password, checked against app_auth.users). identity-service returns an RS256 JWT: sub is the user id, app_metadata.tenant_id and app_metadata.role the tenant and role.
  2. Every call goes through Designer/src/lib/apiClient.ts (apiFetch), which prefixes VITE_API_BASE_URL and attaches the token as a Bearer token.
  3. nginx routes by path prefix and forwards the token untouched.
  4. Each service verifies the token against identity-service's JWKS and scopes every query to the token's tenant.
  5. For writes, flowable-wrapper and design-service ask identity-service for the caller's current role and status (cached up to 30s) instead of trusting the token's role. design-service then sets request.jwt.claims on the transaction so the audit and status triggers record who acted.

4. Running Locally

Native (the everyday setup)

createdb cwp && createdb cwp_spend      # one time
psql -d cwp -f Database/schema.sql -f Database/policies.sql -f Database/local.sql -f Database/roles.sql
./run-local.sh                               # http://localhost:5173  (admin / designer / approver, password "password")

An existing database from before the per-service roles needs only psql -d cwp -f Database/roles.sql. bash Database/check_roles.sh -d cwp proves each role reaches only its own tables. Logs go to .local-logs/.
