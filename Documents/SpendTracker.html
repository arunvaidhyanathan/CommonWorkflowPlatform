0. Decision Summary

Paid API keys are already causing silent failures: the Gemini project hit its monthly spend cap and the OpenRouter key expired, and both were only found by accident. The tracker makes spend and key health visible in the platform itself.

What's Decided (v1)
  • Metering first. Every paid call a CWP service makes is recorded: provider, model, tokens, estimated cost, tenant, feature, outcome. This is real-time and exact for CWP's own calls.
  • Key health for every key. A scheduled, free, read-only check of each key (the same checks as Section 1): valid, expired, invalid, or capped.
  • Provider-reported totals later. Only some providers expose spend by API (Section 2). Those totals include use of the same key by other projects, so they complement metering rather than replace it.
  • Key values never leave the tracker. The UI shows an alias and status only.

3. v1 Design

3.1 Metering

  • The LLM layer in agentic-designer (llm.py) reads token usage from every response (Gemini usage_metadata; OpenAI-compatible usage) and records one usage event per model call, including failed ones (a 429 is exactly what should show up).
  • Usage event: time, service, feature (e.g. generate), provider, model, key alias, tenant id, user id, input and output tokens, estimated cost, latency, outcome (ok, rate_limited, error), and the gateway's X-Request-Id.
  • Events go to the spend-tracker service over the internal Docker network (not through the public gateway), fire-and-forget, so a tracker outage never blocks generation. Dropped events are logged.

3.2 Price table

  • A versioned file of per-model prices (per million input and output tokens) with effective dates, reviewed by a person from each provider's pricing page.
  • A model without a price shows as "unpriced", never as $0, so missing data can't masquerade as free usage. Free-credit hosts (NVIDIA) are recorded with their list price where one exists, or as unpriced.

3.3 Key health

  • The tracker holds the keys it checks in its own environment and runs the Section 1 checks on a schedule (hourly by default) and on demand.
  • Status per key: valid, expired, invalid, capped (inferred from recent metered 429s with a spend-cap message, since a free check can't detect it), unchecked.

3.4 Storage and API

  • Its own database (database per service): a cwp_spend database in the local Postgres container, with usage_events and key_checks tables.
  • POST /events (internal only), GET /summary (spend by provider, model, feature and tenant for a period), GET /keys (status per key), POST /keys/check (run checks now).

3.5 Dashboard

  • An API Spend page in the SPA (next to Administration): month-to-date spend per provider, a daily chart, top models and features, and a key health table. It refreshes every 30 seconds.
  • Access: the keys are the platform operator's, not a tenant's, and CWP has no platform-level role yet (Governance.html Section 3.1). v1 restricts the page to tenant_admin and flags this as a known gap.

3a. S0 as Built: Metering in the Agent Service

Built September 27, 2026 in services/agentic-designer/src/agentic_designer/usage.py and prices.json.

  • Providers report usage. generate_json now returns a Completion (text, input tokens, output tokens). Gemini: prompt_token_count in, candidates_token_count + thoughts_token_count out (thinking is billed as output). OpenAI-compatible: prompt_tokens / completion_tokens. Provider errors carry a kind: rate_limited, error or empty.
  • MeteredProvider wraps the provider for each /generate request and records exactly one event per model call, including every repair attempt and every failure, then returns or re-raises exactly what the provider did. A failing sink is logged and never breaks generation.
  • Live (September 27, 2026): when the renewed OpenRouter key was first checked, its “expired” alert cleared itself (auto: key checked valid) and OpenRouter’s own usage report was stored ($10 key limit). Platform admins are configured via SPEND_ADMIN_USER_IDS (one id set).
  • Features metered: generate, edit, review, and (since A5) embed for grounding’s embedding calls; evaluation runs use eval-*.
  • Context comes from the request: feature generate, tenant and user from the JWT, and the gateway's X-Request-Id, so an event can be matched to the nginx access log line.
  • Sink: for S0, one JSON line per event in the service log (agentic_designer.usage). S1 swaps in a sink that posts to the spend-tracker service; the event is already JSON-serializable as-is.

3b. S1 as Built: The spend-tracker Service

Built September 27, 2026 at services/spend-tracker/ (Python / FastAPI), with its own Postgres (spend-db, database cwp_spend) in Docker Compose.

Access model changed from the original design (Section 3.5)

The design let any tenant_admin see all spend. Because the keys are platform-wide, that would have shown one tenant other tenants' usage, breaking the isolation RLS enforces everywhere else. As built: a tenant_admin sees only their own tenant's spend. Platform-wide spend and key health are limited to user ids listed in SPEND_ADMIN_USER_IDS, which stands in for the platform-level role CWP doesn't have yet (Governance.html Section 3.1). That list is empty until you add your Supabase user id.

Endpoints (through the gateway at /api/spend)

RouteWhoWhat
GET /summary?from=&to=&scope=tenant_admin (own tenant); platform admins (all, or scope=tenant)Totals, and breakdowns by provider, model, feature, tenant (platform scope only) and day. Default range: month to date; at most 366 days; start inclusive, end exclusive
GET /keysPlatform adminsLatest check per key, plus the outcome and time of the last metered call through it and of the last successful one
POST /keys/checkPlatform adminsRun all key checks now
POST /eventsServices only, with X-Ingest-TokenRecord one usage event. The gateway returns 404 for this path, so it is reachable only on the internal Docker network

How it works

  • Delivery: agentic-designer now sends each usage event both to its log and to http://spend-tracker:8095/events. Delivery is fire-and-forget on the event loop, so a slow or down tracker never delays generation; an undelivered event is logged in full so it can be replayed.
  • Totals are honest: the dollar total sums priced calls only. Unpriced calls are counted separately (unpricedCalls). Costs are exact decimal strings.
  • Key checks run at startup and every SPEND_KEY_CHECK_INTERVAL_S (default 3600). Statuses: valid, expired, invalid, missing, error (a network failure is error, never invalid). The key goes in a request header, never the URL. The tracker receives only the four keys it checks.
  • A spend cap shows up anyway: /keys pairs each check with the key's last metered call, so a key whose check says valid but whose last call was rate_limited is visibly in trouble. That is Gemini's exact situation today.
  • Storage: tables usage_events and key_checks, created by numbered SQL migrations applied once each at startup under an advisory lock.

Verified

  • 30 tests against a real Postgres (a throwaway Docker container per test run), covering totals and unpriced counting, breakdowns, range edges, the ingest token, tenant isolation, the platform scope, role refusals, key classification, keys never in URLs, the capped-key view, and migrations applying once. Three deliberately introduced bugs were each caught: dropping the tenant filter (a cross-tenant leak), skipping the ingest token check, and reporting a network failure as an invalid key. Agent service: 92 tests (2 new, for delivery).
  • Live, in the running stack: the first scheduled check reported Gemini valid, NVIDIA valid, OpenRouter expired, TypeSafe valid (the same as the manual check in Section 1). A live NVIDIA generation delivered its event (1,052 in / 346 out tokens, unpriced), and a Gemini call recorded rate_limited. /keys then showed Gemini as check valid with last call rate_limited. Through the gateway: /api/spend/events returns 404; /summary and /keys return 401 without a token.
  • Those two live test events carry tenant and user live-test; they were real calls, so they stay in the data.
  • Not yet verified: /summary and /keys with a real logged-in user through the gateway (they were exercised inside the container and in tests).

3c. S2 as Built: The API Spend Page

Built September 27, 2026: Governance → API Spend in the app (route /spend, Designer/src/pages/SpendPage.tsx), reading /api/spend through Designer/src/data/spend.ts.

  • Who sees it: the nav item and route are shown to tenant_admin. What they see is decided by the service: their own tenant ("Your tenant" badge), or everything for platform admins ("Platform-wide" badge, plus a By tenant table and key health). For a tenant admin who isn't a platform admin, key health shows a "platform admins only" note, and the page stops requesting it after the first refusal.
  • Layout: a range filter in one row above everything (This month, Last 7 days, Last 30 days); four stat tiles (estimated spend, priced calls only; model calls with failures; tokens in and out; unpriced calls); a daily column chart with an Estimated cost / Calls toggle and a Show table view; breakdowns by provider, model, feature and (platform scope) tenant; and the key health table.
  • Key health combines the check with the last real call: Expired / Invalid (critical), Rate-limited (warning: valid key whose last call was refused, which is how the Gemini spend cap shows), Check failed (warning), OK (good), Not configured (neutral). Each status has an icon and a text label as well as its color, and a one-line explanation. Check now runs the checks on demand.
  • Live: refreshes every 30 seconds, and skips refreshes while the browser tab is hidden. Days without calls are shown as zero, so gaps are honest.
  • Chart: hand-built SVG, no new dependency. Single series in the app's brand blue #0066b2, validated against the white surface (all checks pass). Columns at most 24px wide with a 4px rounded top; recessive grid; hover tooltip over the whole day band; drawn at the container's real pixel width so text stays at its size. The app has no dark mode, so none was added here.

Verified

  • Typecheck and lint clean.
  • Rendered with Playwright using a stand-in session and fixture API responses shaped like the real data (a login token isn't available to the build environment), at 1400px and 390px wide, as a platform admin and as a tenant-only admin. No console errors. The first render showed the chart scaling to 1.5× and bars dimming when an empty day was hovered; both were fixed and re-checked. At 390px the page content fits its column; the app shell's fixed sidebar is not built for phones anywhere in the app (pre-existing).
  • The gateway serves the page at /spend.
  • Not yet verified: the page with a real logged-in user against live data, which also needs SPEND_ADMIN_USER_IDS set to see platform scope and key health.

3d. S3 as Built: Budgets, Alerts and Provider-Reported Usage

Built September 27, 2026 in the spend-tracker service (migration 002_budgets_alerts.sql, alerts.py) and the API Spend page.

Budgets

  • One monthly USD budget per provider, or total for everything, set and removed on the API Spend page (platform admins). Compared with this month’s priced spend (UTC). Unpriced calls can’t count toward a budget, and the page says so.
  • Alerts at 80% (warning) and 100% (critical), each once per budget per month, even after it’s dismissed. Setting or lowering a budget evaluates it immediately, so an overspend that already happened is reported now rather than at the next call. Last month’s spend never counts.
  • The page shows each budget as a meter: normal, “! Near budget” or “× Over budget”, with text as well as color.

Alerts

KindRaised whenLevelClears
budgetPriced spend reaches 80% / 100% of a budgetwarning / criticalWhen dismissed; not re-raised that month
key_statusA key check finds the key expired or invalid (never for a network error)criticalAutomatically when a check finds it valid
key_refusedA real call through a key is refused (429: rate limit, quota, spend cap)warningAutomatically when a later call succeeds
provider_limitA provider-reported credit limit has under 20% leftwarningAutomatically when headroom returns

At most one open alert per kind and key, so a key that stays broken doesn’t raise an alert per check. Alerts appear as a banner at the top of the API Spend page (with Dismiss) and as ALERT lines in the service log. Email or Slack delivery is not wired up; nothing in CWP sends notifications yet.

Provider-reported usage

OpenRouter’s key check (GET /api/v1/key) already returns the provider’s own usage, credit limit and remaining credit, so the check now stores them (provider_usage). The key health table shows them (“Provider-reported: $18.50 used of $20.00 limit”). These totals include use of the key outside CWP. Only verified with mocked responses: the real OpenRouter key is expired.

Not built: AWS Cost Explorer (not requested; $0.01 per query; the IAM user lacks ce:GetCostAndUsage).

A bug found on the way

S1’s read queries set row_factory = dict_row on pooled connections. That setting stayed with the connection after it went back to the pool, so the next borrower got dicts instead of tuples. It was harmless until the budget check unpacked rows, and a budget test caught it. Read queries now set the row factory on their own cursor only.

Verified

  • 52 spend-tracker tests (22 new) against real Postgres: thresholds once each, immediate evaluation on budget change, unpriced exclusion, total budgets, no re-raise after dismissal, month boundaries, validation, platform-admin-only access, refused-call alert and auto-clear (and a new alert after recovery), expired-key alert once across repeated checks and auto-clear, no alert for network errors, OpenRouter usage parsing, the low-credit alert, and provider messages instead of raw JSON in alert text. Three deliberately introduced bugs were each caught.
  • Live, on the real database: migration 002 applied; the first key check raised a critical alert for the expired OpenRouter key; a real Gemini call (refused by the spend cap) raised a key_refused warning through the full path (agent service → delivery → tracker). Those are the project’s two real incidents.
  • The page’s new parts (alert banner, budget meters and form, provider-reported line) rendered with fixture data at 1400px with no console errors.
  • The open OpenRouter alert was raised before provider error messages were cleaned up, so its text still includes the raw error body; new alerts use the clean message.

5. Risks & Open Questions

  • Metering only sees CWP's calls. The same keys are used by other projects in ~/Developer. For Gemini and NVIDIA, which have no spend API, the tracker can't show total account spend.
  • Estimated, not billed, cost. Prices change and providers round differently; the dashboard labels figures as estimates.
  • Shared secrets file. ~/Developer/.env holds keys for several projects, including AWS and database credentials. The tracker should receive only the keys it checks, not the whole file.
  • No platform-level role. Handled for now with SPEND_ADMIN_USER_IDS (Section 3b); replace it when Governance.html's platform role exists.
