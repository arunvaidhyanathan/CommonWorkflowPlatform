0. Scope & How This Relates To The Other Docs

Current State, September 27, 2026

Names changed on this date. The Java "Runtime Gateway" is now the workflow-runtime service (services/workflow-runtime/, formerly WaaS/Workflow-Wrapper). A standalone nginx edge gateway (gateway/) now fronts every CWP service: /api/runtime/** goes to workflow-runtime and /api/agent/** to the new agentic-designer. In the SPA, lib/runtimeGatewayClient.ts is now lib/apiClient.ts, and VITE_RUNTIME_GATEWAY_URL is now VITE_API_BASE_URL (the gateway's /api prefix). Older text below keeps the old names for historical accuracy. See Services.html.

Data impact: the design-time public schema is unchanged. For local development, workflow-runtime's runtime schema and Flowable's engine tables now live in their own Postgres container (runtime-db in Docker Compose) instead of the shared database, following a database-per-service rule; production can still point at the shared database's runtime schema through WORKFLOW_RUNTIME_DB_* environment variables (formerly RUNTIME_GATEWAY_DB_*).

CWP.html Section 2 already states the platform's foundation in one line: a single PostgreSQL database with row-level security as the tenant isolation boundary. Designer.html Section 3 sketches the schema DDL and Section 2 sketches the RLS pattern; Governance.html documents the role model these policies enforce. This document is the missing piece between those sketches and reality: the complete, current data catalog (every column, constraint, index, and default -- not just the illustrative subset each component doc needed), a single entity-relationship diagram tying all nine tables together, the actual function/trigger bodies that make audit logging and status transitions work, the full RLS policy catalog, and process-flow diagrams for the flows that touch the most tables (workflow lifecycle, invites, audit trail, tenant isolation).

What's Deliberately Out Of Scope Here

The Runtime Gateway's own runtime schema (WorkflowWrapper.html) and Flowable's ACT_* engine tables are separate, Liquibase-managed schemas owned by that Java service -- cataloging them here would create a second, driftable source of truth for something already documented and versioned elsewhere. Section 7 flags one live finding from that schema (an RLS gap) because it's a genuine risk worth surfacing, but the full catalog stays in WorkflowWrapper.html.

1. Multi-Tenancy & Identity Model

Every tenant-scoped table carries a tenant_id column, and every RLS policy that reads or writes tenant data checks it against current_tenant_id() -- a SQL function that extracts the claim from the caller's JWT. Three helper functions form the entire authorization vocabulary every policy in Section 5 is built from:

FunctionReturnsReadsUsed By
current_tenant_id()uuidJWT app_metadata.tenant_id claimEvery tenant-scoped SELECT/INSERT/UPDATE/DELETE policy
current_role_claim()textJWT app_metadata.role claimEvery write policy that's role-gated (designer/tenant_admin/approver)
current_user_id()uuidJWT sub claim (the standard JWT subject -- "who is this")profiles self update, the approval-decision self-approval block, every audit trigger's actor_id
is_current_user_active()booleanprofiles.status for current_user_id()Every write policy, so a deactivated member loses write access immediately without deleting their row (Governance.html Section 8)
Single Token, Every Layer

The same JWT that authorizes a direct database read (via RLS, above) also authorizes calls to the Runtime Gateway (WorkflowWrapper.html Section 7) -- there is exactly one credential in the entire system, and tenant identity cannot diverge between the two planes because both read the same app_metadata claim. The Runtime Gateway isn't subject to RLS (it connects as a privileged JDBC role, not through the anon/authenticated REST path), so it re-derives the same tenant scoping in application code instead -- a second place the same logic has to be gotten right, flagged as a standing risk in WorkflowWrapper.html Section 10.

Where the identity behind sub/sign-in actually lives is a separate concern from this schema. profiles.id is a foreign key to whatever issues JWTs -- on the live database, that's the auth service's own user table. This schema doesn't create or own that table (Section 8 covers what that means for exporting to a new database).

4. Functions & Triggers Catalog

Ten functions do all the work: four are the auth-claim helpers from Section 1, one is a portability-relevant email sync, and five are audit/status triggers. All are SECURITY INVOKER (the default) except where the underlying platform's trigger execution model grants elevated write access to audit_logs despite that table having no client-facing INSERT policy -- triggers execute with the privileges needed to complete their defined action regardless of the RLS policies that would otherwise block the invoking role, which is exactly why audit logging can't be bypassed by a client that simply avoids calling an API layer.

FunctionFires OnEffect
audit_approval_decision()approval_requests UPDATE, when status changes to approved/rejectedInserts an approval_decided row into audit_logs
audit_profile_status_change()profiles UPDATE, when status changesInserts a profile_status_changed row
audit_workflow_archive()workflows UPDATE, when status becomes archivedInserts a workflow_archived row
audit_workflow_delete()workflows DELETEInserts a workflow_deleted row (captures name/status/definition_key from the deleted row, since it won't exist to look up afterward)
sync_workflow_status_from_approval()approval_requests INSERT/UPDATEInsert → flips parent workflows.status to pending_approval. Update to approved/rejected → flips to approved/draft. This is how the client never writes workflows.status for the approval lifecycle directly (Designer.html Section 21.4)
reset_workflow_status_on_new_version()workflow_versions INSERTIf the parent workflow's status was approved, resets it to draft and logs a workflow_status_reset_on_edit row -- the fix described in Designer.html Section 22.4
sync_profile_email()Auth-provider user-table UPDATE (email change) -- lives on the identity table, not on anything in this catalogMirrors the new email into profiles.email, so Administration's team list can show it without querying the identity table directly (Designer.html Section 22.5)
One Trigger Gap, Noted Not Fixed

Saving a new version while a workflow is pending_approval is not blocked and does not auto-withdraw the stale request -- the pending approval_requests.version_id can end up pointing at a superseded version. This was flagged, not fixed, when reset_workflow_status_on_new_version() was built (Designer.html Section 22.4) and remains open.

7. Known Gaps & Risks

  • A live security-advisor check found runtime.deployments has Row-Level Security disabled. Unlike every table in this catalog, that table (in the Runtime Gateway's own schema, WorkflowWrapper.html) is fully readable/writable by any authenticated -- and possibly anonymous -- API caller today. This is a pre-existing gap surfaced while building this document, not something introduced by it. Recommended fix, deliberately not applied automatically (enabling RLS with zero policies would block all access, including the Runtime Gateway's own reads, unless it connects as a role that bypasses RLS -- verify which role before flipping this): 
    alter table runtime.deployments enable row level security;
-- then add a tenant-scoped policy before relying on this being protected
  • Identity lives outside this schema. Every FK that ultimately traces to "which user" (profiles.id, and transitively every *_by/actor_id column) depends on an auth provider's user table that this catalog doesn't own or control. Section 8 covers what that means for a schema export.
  • No unique constraint on invites (tenant_id, email). Re-inviting the same address creates a second row rather than updating the existing one. Not a reported problem today; worth a decision if it becomes one.
  • The stale-pending-approval gap from Section 4's callout: saving a new version during pending_approval doesn't block the save or auto-withdraw the stale request.
  • profiles has no secondary index on tenant_id. Every current query path reaches it via id or RLS filtering rather than a tenant-scoped list query, so this hasn't mattered yet -- worth revisiting if a "list all members of my tenant" query path is added without going through id.

Database/schema.sqlEvery table, constraint, and index in this catalog, as portable DDL -- runs on any Postgres 14+, no Supabase-specific objects. Includes an app_auth.users stand-in table so profiles.id's FK has somewhere real to point, since this schema doesn't own identity (Section 7)
Database/policies.sqlThe four auth-claim helper functions (reimplemented using the underlying current_setting('request.jwt.claims', true) mechanism instead of Supabase's auth.jwt()/auth.uid() wrappers -- see the file's own portability note for why this is a drop-in-compatible change), every RLS policy from Section 5, and every trigger from Section 4
Database/MIGRATION.mdThe actual data export/import plan: pg_dump/psql commands, FK-safe load ordering, and -- the genuinely hard part -- three concrete options for handling identity (keep the existing auth provider, migrate to a new one with ID remapping, or stand up the placeholder app_auth.users for real), plus a post-load verification checklist that tests RLS behaviorally, not just structurally
Why The Runtime Schema And Flowable's Engine Tables Aren't In These Scripts

Both are Liquibase-managed by the Runtime Gateway itself (WaaS/Workflow-Wrapper/src/main/resources/db/changelog/ for runtime; Flowable's own internal Liquibase for ACT_*, triggered by flowable.database-schema-update=true on first boot). Provisioning a new database's copy of either means running that service's migrations against it, not hand-copying SQL here -- doing the latter would create a second, driftable definition of the same schema.

Quick start (full detail in MIGRATION.md):

psql "$TARGET_DATABASE_URL" -f Database/schema.sql
psql "$TARGET_DATABASE_URL" -f Database/policies.sql
# then export/import data per MIGRATION.md's Steps 2-5,
# after deciding how to handle identity (MIGRATION.md Step 2)
