0. Decision Summary

CWP.html has listed Workflow Wrapper as explicitly out of scope since the platform index was written: "nothing to design yet; revisit once the design-time components are stable." A detailed brief of Flowable-engine-driven improvements across all four other components made clear that revisit point has arrived -- app packaging, one-click deploy, dynamic form rendering, CMMN plan-item visibility, tenant-aware seed bundles, and engine-native audit history all require an actual backend service talking to a workflow engine, which today does not exist anywhere in this platform.

What's Decided Here

A new Java / Spring Boot microservice -- the Runtime Gateway -- is the architectural answer, built first as a thin API layer with no live Flowable engine behind it (Section 5), because Flowable's current stable line does not yet run on Spring Boot 4 (Section 4). This document is the map for that build; it does not implement anything -- see Section 9 for what's actually scheduled and in what order.

Update, August 3, 2026: Phase 1 Scaffolded

Phase 1 and Governance's Phase 4 deploy-authority check (Section 9) have been scaffolded at WaaS/Workflow-Wrapper: the Maven project, JWT-to-Spring-Security wiring against the auth service's JWKS endpoint (Section 7), Liquibase migrations for the runtime schema (already applied to the live PostgreSQL database), a working /runtime/deployments API gated by a tenant_admin-only deploy-authority check, and stub controllers for the three not-yet-real endpoints in Section 8. See that project's README.md for exact status, configuration, and the one thing this update cannot claim: the code has not been compiled or run anywhere, since this was written in a sandbox without a JDK/Maven/network environment to verify it in.

Update, September 27, 2026: No Longer Called a Gateway

The "Runtime Gateway" name is retired. Its real job is hosting Flowable, so it is now workflow-runtime (services/workflow-runtime/), and a standalone nginx edge gateway sits in front of it and every other CWP service. It compiled and booted for the first time on this date. See Section 11 and Services.html. Older text below keeps the old name for historical accuracy.

Update, same day: Phase 2 (Designer Publish) Also Built

The Runtime Gateway's deployment contract was extended with a real manifest field (Section 8), and Designer.html now has a working Publish button (Section 23.3) calling it end to end, gated to tenant_admin accounts. Unlike the Java service, this frontend change runs in a normal Node/Vite environment and was verified with tsc -b (zero type errors) -- a real build/lint pass (vite build, oxlint) could not complete in this session's sandbox due to missing native bindings for its CPU architecture, unrelated to the change itself. The Java side of this update (the new manifest/manifest_json column and ManifestArtifact DTO) carries the same uncompiled/unverified caveat as the rest of the Runtime Gateway above.

1. Why This Component Exists Now

Every improvement in the originating brief shares the same blocker: they all assume a running Flowable engine (or something that behaves like one) sitting behind the app, reachable over REST. .bar app packaging, one-click deploy, historic task/activity queries, CMMN plan-item state, and dynamic form rendering are all Flowable engine capabilities -- none of them can be built as another serverless function or another React component alone. That's the entire reason Workflow Wrapper stayed unstarted this long: there was nothing concrete to design against until a specific set of engine-dependent features was on the table.

2. Node vs. Java: What's Actually There Today

Directly answering the question that prompted this document: there is no Node.js backend anywhere in CWP to pivot away from. What exists today, per CWP.html Section 2 and Designer.html:

LayerWhat It Actually Is
FrontendVite + React 19 + TypeScript SPA at WaaS/Designer -- a browser application, not a server
"Backend" todayPostgreSQL + RLS + a JWT-based auth service, plus two serverless functions (admin-set-role, invite-user) running on a request-scoped runtime, not a persistent server process
Runtime engineNone. No Flowable, no BPMN/CMMN execution of any kind exists yet -- every workflow built in Designer today is design-time only, never actually run

So: yes, introducing a Java/Spring Boot service is unambiguously additive, not a migration. Nothing needs to be rewritten or decommissioned to make room for it.

Why A New Schema, Not A New Database

A second, fully separate database would mean a second source of truth for tenant identity, and every runtime-shaped query (e.g., "show me this tenant's process instances") would need to re-derive or re-fetch tenant context that the PostgreSQL database already owns. A dedicated runtime schema in the same Postgres instance keeps one tenant registry (public.tenants) while giving the Java service full ownership -- its own migrations, its own tables, no RLS dependency -- over the shape workflow-runtime data actually needs, which is very different from the design-time shape public.workflows already has.

4. The Flowable / Spring Boot 4 Compatibility Risk (Resolved)

Correction, August 3, 2026: This Was Checked Late, But It's Resolved

This section originally said Flowable's stable line (7.x) didn't run on Spring Boot 4 and that Flowable 8 had "no confirmed date." That was true when first written, but Flowable Open Source 8.0.0 shipped February 26-27, 2026 -- five months before this correction -- with official Spring Boot 4 / Spring Framework 7 support (Jakarta EE 11), dropping Spring Boot 3 support entirely. org.flowable:flowable-spring-boot-starter:8.0.0 is a real, published Maven Central artifact. The original research (a forum thread about Flowable 7.2.0 failing on Spring Boot 4) was accurate for its moment but was never rechecked against a newer release before the "thin API layer, no live engine" decision below was made and built. It should have been rechecked before Phase 1 was scaffolded, not five weeks into building on top of that assumption. See Section 9 for what changed once this was caught.

Original text, kept for the record: Flowable's then-current stable engine line (7.x) targeted Spring Boot 3 / Spring 6 / Jakarta EE 9-10. Spring Boot 4.0 requires a Jakarta EE 11-compliant stack. A live Flowable community forum thread reported Flowable 7.2.0 does not work with Spring Boot 4, with full Spring Boot 4 support planned for a future Flowable 8 release that had no confirmed date at the time.

What's Actually True Now

Flowable 8.0.0's flowable-spring-boot-starter bundles the Process (BPMN), CMMN, DMN, and IDM engines and is fully compatible with this project's Spring Boot 4.0 / Java 21 stack -- no separate sidecar process, no dependency conflicts (Java 21, not 25 -- see Section 3's correction). One real gap remains, found while re-researching this: the standalone Flowable Form Engine (a separate deployable form-definition repository with its own FormRepositoryService) was deprecated as of Flowable 7.0.1 and is not part of this starter. Forms are now handled through the Process/CMMN engine's own built-in FormService (task/start forms tied to a process or case definition, not an independently versioned resource) -- a materially different shape than what Section 8's original API sketch and the originating brief's GET /form-repository/form-definitions/{id} assumed. That gap is real and unresolved -- see Section 9 Phase 3 and Section 10.

5. Architecture: Runtime Gateway Embedding a Real Flowable Engine

Update, August 3, 2026

This section originally described a "thin API layer" with application logic mimicking Flowable, because Section 4's compatibility risk (now resolved) ruled out embedding the real engine. That's no longer the plan: Flowable 8.0.0's flowable-spring-boot-starter runs embedded, in-process, inside the Runtime Gateway itself -- same JVM, same Spring context, no sidecar. The diagram and description below describe the corrected, current architecture.

The Runtime Gateway is the single Java service every runtime-shaped feature in Sections 6-9 talks to. It embeds Flowable's Process (BPMN), CMMN, DMN, and IDM engines directly (flowable-spring-boot-starter) and exposes its own /runtime/* REST contract on top -- deliberately not Flowable's own bundled REST API (flowable-spring-boot-starter-rest), which would introduce a second, differently-secured API surface (Flowable's REST modules assume IDM/Basic-Auth-style security) alongside our own JWT-secured one. Keeping our own controller layer as the only public surface preserves the "Single Token, Two Planes" model in Section 7 and lets deploy-authority (Governance Section 11.3) stay enforced in one place.

Concretely: a deploy request now calls Flowable's real RepositoryService/CmmnRepositoryService/DmnRepositoryService to deploy the manifest's actual BPMN/CMMN/DMN XML, tagged with the caller's tenant_id via Flowable's own native multi-tenancy (tenantId on the deployment builder) -- not a synthetic ID. The runtime.deployments row still exists, but now as a tenant-scoped audit/traceability record pointing at the real Flowable deployment ID(s), consistent with the "why a new schema" reasoning in Section 3. Case-instance and history queries now read from Flowable's own CmmnRuntimeService/HistoryService, not application-level bookkeeping. The one thing still not real: form rendering, because the standalone Form Engine those endpoints were modeled on no longer exists (Section 4) -- Section 9 Phase 3 needs its own redesign before that stub becomes real.

7. Data & Auth Model

Mirrors the "Single Token, Two Planes" pattern Designer.html Section 2.2 already anticipated for exactly this component (its enforcement-points table already had a "Spring Boot Wrapper" row, unbuilt until now): the same auth-service-issued JWT that authorizes Postgres RLS also authorizes calls to the Runtime Gateway. The gateway validates the JWT against the auth service's JWKS endpoint (no shared secret, no second credential), extracts tenant_id/role from app_metadata the same way current_role_claim()/current_tenant_id() do in Postgres, and scopes every query in the runtime schema by tenant accordingly -- application-level tenant isolation, since the Java service isn't subject to Postgres RLS the way the anon-key client is.

A New Trust Boundary To Get Right

Because the Runtime Gateway connects to Postgres directly (not through the anon-key/RLS path), it is a privileged component by construction -- more like the service-role side of a serverless function than like the browser client. Every handler must explicitly filter by the caller's tenant_id; there is no database-enforced backstop the way RLS provides for the SPA. This is the same category of risk CWP.html's "privileged writes go through serverless functions" principle was written to manage, just for a new kind of privileged component.

public.deployments vs. runtime.deployments -- Not The Same Table

The original CWP schema already has an (unused, zero-row) public.deployments table, described in Designer.html as a traceability bridge between PostgreSQL workflow versions and eventual Flowable deployments. The Runtime Gateway's Phase 1 scaffold deliberately does not reuse it -- it owns a separate runtime.deployments table in the new schema instead, with no foreign key or sync between the two. This avoids taking a cross-schema dependency on a Postgres/RLS-owned table from application code that has no RLS backstop of its own. If public.deployments is ever activated for its originally-intended purpose, reconcile the two explicitly rather than letting them silently drift -- this has not been decided yet and is flagged here so it isn't forgotten.

10. Risks & Open Questions

  • Dynamic form rendering has no clear target API anymore. The standalone Flowable Form Engine (FormRepositoryService) that Section 8's original sketch and Workbench.html 2B were scoped against was deprecated as of Flowable 7.0.1. The Process/CMMN engine's own FormService is the current mechanism, but it's tied to a specific process/case definition's embedded form key rather than an independently browsable, versioned repository -- Designer.html Section 23.2 and Workbench.html Section 7.2 need a real redesign pass against Flowable 8's actual API before this is buildable, not just a "wire it up" task.
  • [Resolved September 27, 2026: compiles and boots; see Section 11.] Embedding Flowable is new, uncompiled surface area on top of an already-uncompiled service. The Process/CMMN/DMN engine wiring in DeploymentService, CaseInstanceController, and TaskInstanceHistoryController was written against Flowable's documented public API (RepositoryService, CmmnRepositoryService, DmnRepositoryService, CmmnRuntimeService, HistoryService) but has never been compiled -- this is a materially bigger and riskier piece of uncompiled code than Phase 1's original thin layer. Treat mvn clean verify as non-optional before deploying this anywhere.
  • [Resolved September 27, 2026: observed on first boot. Our changelog ran all 8 changesets and Flowable created its own tables alongside; see Section 11.] Flowable's own Liquibase usage vs. this project's Liquibase usage. Flowable 8 uses Liquibase internally to manage its own engine tables and sets spring.liquibase.enabled=false by default specifically so a host app's own Liquibase setup doesn't collide with it. This project already sets spring.liquibase.enabled: true explicitly for the runtime schema changelog (Section 3) -- per Flowable's own docs this should only affect our changelog, not Flowable's internal one, but this interaction has not been observed running and is worth confirming on first real boot.
  • Application-level tenant isolation is a new risk category. Every Runtime Gateway handler is hand-responsible for tenant scoping (Section 7) -- worth a dedicated test suite the same way Designer.html Section 20.4 calls for one for RLS, but for this service instead. This now also covers the tenant ID passed into Flowable's own multi-tenancy (Section 5), which is a second place tenant scoping can silently go wrong.
  • [Resolved September 27, 2026: builds in Docker with Maven + Temurin 21.] Java 21 / Spring Boot 4 in this project's actual dev/deploy environment hasn't been validated. This session's sandbox has neither (Java 11 only, no Docker, no Maven) -- this scaffold needs to be built and verified somewhere that has them, which is an environment decision outside this document's scope.

The service was renamed and put behind a standalone nginx edge gateway (Services.html). Its HTTP paths did not change: the gateway maps /api/runtime/** to the service's /runtime/**.

Fixes needed for the first compile and boot

The code had never been compiled. Getting it to boot took five fixes:

  • pom.xml was not valid XML: its comments contained --, which XML forbids inside comments.
  • Jackson 3: Spring Boot 4 ships Jackson 3, so com.fasterxml.jackson.* imports became tools.jackson.*, and JsonProcessingException became JacksonException (in DeploymentService).
  • Moved classes: MacAlgorithm is in org.springframework.security.oauth2.jose.jws (Spring Security 7); HistoricTaskInstance is in org.flowable.task.api.history.
  • Roles were never mapped (a real bug): SecurityConfig used the no-argument jwt() configurer, which Spring Security 7 removed. Even before that, the SupabaseJwtAuthenticationConverter bean was never applied, because Spring only auto-detects a bean of type JwtAuthenticationConverter. It is now wired explicitly, so app_metadata.role becomes ROLE_* authorities as Section 7 intended.
  • Liquibase never ran: Spring Boot 4 moved Liquibase auto-configuration into its own module, so liquibase-core alone did nothing and Hibernate's validate failed on the missing runtime.deployments table. Replaced with spring-boot-starter-liquibase.

Verified

  • Boots in about 5 seconds; all 8 Liquibase changesets apply to a fresh database; Flowable creates its engine tables in the runtime schema (65 tables in total there).
  • Through the gateway: GET /api/runtime/deployments returns 401 with no token and with a malformed one.
  • Not yet verified: an authenticated call and a Publish from the SPA through the gateway. There are still no automated tests in this service.
