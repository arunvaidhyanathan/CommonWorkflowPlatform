0. Architecture Decision Summary

Current State, September 27, 2026

Names changed on this date. The Java "Runtime Gateway" is now the workflow-runtime service (services/workflow-runtime/, formerly WaaS/Workflow-Wrapper). A standalone nginx edge gateway (gateway/) now fronts every CWP service: /api/runtime/** goes to workflow-runtime and /api/agent/** to the new agentic-designer. In the SPA, lib/runtimeGatewayClient.ts is now lib/apiClient.ts, and VITE_RUNTIME_GATEWAY_URL is now VITE_API_BASE_URL (the gateway's /api prefix). Older text below keeps the old names for historical accuracy. See Services.html.

New in the editor: a Generate with AI toolbar button (BPMN only, for designers and tenant admins) opens the Agentic Designer panel in place of the properties panel. It drafts a workflow from a plain-language description and places it on the canvas as unsaved changes; saving and approval work as before. See AgenticDesigner.html Section 4a. The workflow-runtime service also compiled and booted for the first time on this date (WorkflowWrapper.html Section 11).

Decision Log
  • Persistence: PostgreSQL is the design-time source of truth. Workflows, versions, forms, and deployment records live in PostgreSQL under RLS. Flowable only receives deployed XML.
  • Identity: A JWT-based auth service end-to-end. The auth service issues JWTs; RLS isolates tenants at the database; the Spring Boot wrapper validates the same JWT (against the auth service's JWKS endpoint) and derives the tenant from claims.
  • Frontend: Vite + React 19 SPA. Browser-only Postgres REST client (createBrowserClient); no SSR middleware.
  • Collaboration: Single-editor v1 with a lock flag on the workflow row. Live co-editing deferred to v2.
  • Engine access: The SPA never calls Flowable REST directly. All runtime operations route through the Spring Boot wrapper.
  • Round-trip editing: The Designer is a full editor, not just an authoring tool. Existing BPMN 2.0 definitions import from file, from PostgreSQL history, or from the running Flowable engine, and re-serialize losslessly (ISO 19510 XML interchange).
  • Workflow identity: Process ID (definition key) and name are user-controlled, captured at creation or import, validated for uniqueness per tenant, and preserved across versions.

Key Architectural Layers

  • Canvas Presentation Layer: Renders custom nodes, sequence flows, sentries, and decision trees using @xyflow/react.
  • State & Command Layer: Powered by Zustand with transactional mutations, zundo undo/redo history, and active selection tracking.
  • Moddle Translation Pipeline: Translates visual graph JSON into OMG-compliant XML definitions (BPMN 2.0, CMMN 1.1, DMN 1.3) required by Flowable.
  • Design-Time Repository: PostgreSQL stores graph JSON and generated XML per version, with tenant-scoped RLS.
  • Runtime Gateway: The Spring Boot wrapper is the only component that touches Flowable APIs; it validates JWTs and enforces tenant isolation on every call.

2. Identity, Multi-Tenancy & Row-Level Security

A JWT-based auth service is the single identity provider. Tenant membership and role are written to app_metadata at user provisioning time, making them tamper-proof claims inside every JWT.

2.1 JWT Claim Contract

{
  "sub": "7c1e...user-uuid",
  "email": "designer@tenant-a.com",
  "app_metadata": {
    "tenant_id": "a2f4...tenant-uuid",
    "role": "designer"   // designer | admin | viewer
  }
}

2.2 Enforcement Points

Layer Mechanism What It Protects
PostgreSQL RLS policies keyed on current_setting('request.jwt.claims', true)::json -> 'app_metadata' ->> 'tenant_id' All design-time rows (workflows, versions, forms)
Spring Boot Wrapper JWT validation against the auth service's JWKS endpoint; tenant claim mapped to X-Tenant-ID and Flowable tenant queries Deployments, process instances, tasks, telemetry streams
Flowable Core Native tenantId column on deployments and instances Engine-level data partitioning
Single Token, Two Planes

The same auth-service-issued JWT authorizes both direct database access (via RLS) and wrapper API calls. There is no second credential exchange, and tenant identity cannot diverge between planes because both read the same claim.

3.2 RLS Policies

alter table workflows enable row level security;

-- Helper: current tenant from JWT app_metadata
create function current_tenant_id() returns uuid
language sql stable as $$
  select ((current_setting('request.jwt.claims', true)::json -> 'app_metadata') ->> 'tenant_id')::uuid
$$;

create policy "tenant read" on workflows
  for select using (tenant_id = current_tenant_id());

create policy "designer write" on workflows
  for all using (
    tenant_id = current_tenant_id()
    and ((current_setting('request.jwt.claims', true)::json -> 'app_metadata') ->> 'role') in ('designer', 'admin')
  );

4. Workflow Lifecycle: Origination, Save, Version, Deploy, Rollback

4.1 Origination Paths

A workflow enters the Designer through one of four paths. All converge on the same canvas state and lifecycle; imported definitions are first-class citizens, fully editable.

Path Source Mechanics
New Blank canvas Identity dialog (4.2) creates the workflows row and an empty draft version
Import file Uploaded .bpmn20.xml / .cmmn / .dmn Moddle adapter parses XML to graph; evaluator (Section 12) runs immediately; DI bounds honored, auto-layout (elkjs) applied where DI is absent
Import from engine Deployed definition in Flowable Wrapper endpoint GET /api/v1/tenants/{t}/definitions/{key}/xml fetches the resource; imported as a new workflow or as a new version of an existing one (matched by definition key)
Open existing PostgreSQL workflow_versions Any historical version opens read-only; "Edit as new draft" branches it into the current draft

4.2 Workflow Identity Capture

On create and on import, an identity dialog captures and validates the definition's identity before the canvas opens:

  • Process ID (definition key): user-chosen, slug-validated (^[a-zA-Z_][a-zA-Z0-9_-]*$), unique per tenant (enforced by a unique (tenant_id, definition_key) constraint added to workflows). This key is what Flowable uses to correlate versions of the same process, so it is immutable after first deploy; the dialog warns before locking it.
  • Name and description: free-text, editable at any time, serialized into the XML (name attribute, documentation element).
  • On import: the dialog pre-fills ID and name parsed from the XML and lets the user confirm or override. If the key already exists for the tenant, the user chooses: import as new version of that workflow, or rename to a new key.
-- Addition to the workflows table (Section 3)
alter table workflows add column definition_key text not null;
alter table workflows add column description text;
alter table workflows add constraint workflows_tenant_key_unique
  unique (tenant_id, definition_key);

4.3 Save, Version, Deploy, Rollback

  1. Autosave (draft): The editor debounces canvas mutations and upserts graph_json into the workflow's draft version row. No XML generation on autosave.
  2. Save Version: Explicit action. The moddle adapter serializes the graph to XML; both graph_json and xml_content freeze into a new immutable workflow_versions row (version_no + 1); current_version_id advances.
  3. Deploy: The SPA posts the frozen XML to the wrapper. On Flowable success, the wrapper returns flowable_deployment_id, which the SPA records in deployments. Prior active deployment rows for the workflow flip to superseded.
  4. Rollback: Redeploy any historical version. A rollback is just a deploy of an older workflow_versions row; history is never rewritten.
Single-Editor Lock (v1)

Opening a workflow for editing sets locked_by / locked_at. Other users get read-only mode with the lock owner surfaced. Locks expire after inactivity (e.g. 15 minutes) and admins can force-release. Live co-editing via a Postgres change-stream/realtime layer is deferred to v2.

5.2 Full Editor Feature Set

The Designer targets a complete modeling experience, on par with dedicated BPMN tooling:

  • Element palette: categorized by the OMG element taxonomy — Flow Objects (events, activities, gateways), Connecting Objects (sequence, message, association), Swimlanes (pools, lanes), Artifacts (data objects, groups, annotations) — with drag-to-canvas and click-to-place.
  • Dual view — canvas and XML source: a CodeMirror XML panel alongside the canvas with two-way sync. Manual XML edits re-parse through the moddle adapter and update the graph; canvas edits re-serialize to the source panel. Parse errors pin to the offending line without losing canvas state.
  • Canvas ergonomics: minimap, snap-to-grid, alignment and distribution guides, marquee multi-select, copy/paste (in-canvas and cross-workflow), context menus, and keyboard shortcuts (delete, duplicate, undo/redo, zoom-to-fit).
  • Auto-layout: elkjs layered layout for imported definitions lacking Diagram Interchange (DI) coordinates, and as an on-demand "tidy up" action.
  • Interchange fidelity: moddle preserves unknown namespaces and vendor extension attributes on round-trip, so a definition imported from another ISO 19510-conformant tool (or from Flowable Modeler) re-exports without losing extension data the canvas does not render.
  • Export: download as .bpmn20.xml / .cmmn / .dmn, or as SVG/PNG snapshots of the diagram.

6. Centralized State Engine (Zustand Architecture)

The canvas store isolates graph rendering state, spec context, and underlying XML models. Implemented with zundo for full undo/redo state tracking.

import { create } from 'zustand';
import { temporal } from 'zundo';
import { Node, Edge, OnNodesChange, OnEdgesChange, applyNodeChanges, applyEdgeChanges } from '@xyflow/react';

export type SpecType = 'BPMN' | 'CMMN' | 'DMN';

export interface NodeData {
  label: string;
  documentation?: string;
  assignee?: string;
  candidateGroups?: string[];
  delegateExpression?: string;
  conditionExpression?: string;
  formKey?: string;
  [key: string]: any;
}

interface WorkbenchState {
  // Workspace Context
  activeSpec: SpecType;
  workflowId: string;
  draftVersionId: string | null;
  tenantId: string;
  isDirty: boolean;

  // Graph Model
  nodes: Node<NodeData>[];
  edges: Edge[];
  selectedNodeId: string | null;

  // Actions
  setActiveSpec: (spec: SpecType) => void;
  onNodesChange: OnNodesChange;
  onEdgesChange: OnEdgesChange;
  selectNode: (id: string | null) => void;
  updateNodeData: (id: string, data: Partial<NodeData>) => void;
  addNode: (node: Node) => void;
  setGraph: (nodes: Node[], edges: Edge[]) => void;
}

export const useWorkbenchStore = create<WorkbenchState>()(
  temporal((set, get) => ({
    activeSpec: 'BPMN',
    workflowId: '',
    draftVersionId: null,
    tenantId: '',
    isDirty: false,

    nodes: [],
    edges: [],
    selectedNodeId: null,

    setActiveSpec: (activeSpec) => set({ activeSpec }),

    onNodesChange: (changes) => set({
      nodes: applyNodeChanges(changes, get().nodes),
      isDirty: true,
    }),

    onEdgesChange: (changes) => set({
      edges: applyEdgeChanges(changes, get().edges),
      isDirty: true,
    }),

    selectNode: (selectedNodeId) => set({ selectedNodeId }),

    updateNodeData: (id, data) => set({
      nodes: get().nodes.map((node) =>
        node.id === id ? { ...node, data: { ...node.data, ...data } } : node
      ),
      isDirty: true,
    }),

    addNode: (node) => set({
      nodes: [...get().nodes, node],
      isDirty: true,
    }),

    setGraph: (nodes, edges) => set({ nodes, edges, isDirty: false }),
  }))
);

Autosave subscribes to isDirty transitions and debounces an upsert of the serialized graph into the draft workflow_versions row via the Postgres REST client.

7. Bidirectional Moddle Schema Adapter Engine

Conversion between Flowable-compatible XML definitions and internal React Flow canvas structures. One adapter per specification, sharing a common ModdleParseResult contract.

7.1 BPMN Adapter

import BpmnModdle from 'bpmn-moddle';
import { Node, Edge } from '@xyflow/react';

const moddle = new BpmnModdle();

export interface ModdleParseResult {
  nodes: Node[];
  edges: Edge[];
  processId: string;
}

/**
 * Deserializes standard BPMN 2.0 XML into React Flow Graph State
 */
export async function parseBpmnXml(xmlString: string): Promise<ModdleParseResult> {
  const { rootElement } = await moddle.fromXML(xmlString);
  const process = rootElement.flowElements ? rootElement : rootElement.rootElements[0];

  const nodes: Node[] = [];
  const edges: Edge[] = [];

  (process.flowElements || []).forEach((element: any) => {
    if (element.$type === 'bpmn:SequenceFlow') {
      edges.push({
        id: element.id,
        source: element.sourceRef.id,
        target: element.targetRef.id,
        label: element.name || '',
        type: 'smoothstep',
        data: {
          conditionExpression: element.conditionExpression?.body,
        },
      });
    } else {
      // Read Diagram Interchange (DI) position bounds if present
      const bounds = element.di?.bounds || { x: 150, y: 150 };
      nodes.push({
        id: element.id,
        type: mapModdleToReactFlowNode(element.$type),
        position: { x: bounds.x, y: bounds.y },
        data: {
          label: element.name || element.id,
          documentation: element.documentation?.[0]?.text,
          assignee: element.assignee,
          delegateExpression: element.delegateExpression,
        },
      });
    }
  });

  return { nodes, edges, processId: process.id };
}

function mapModdleToReactFlowNode(type: string): string {
  switch (type) {
    case 'bpmn:StartEvent': return 'startEvent';
    case 'bpmn:EndEvent': return 'endEvent';
    case 'bpmn:UserTask': return 'userTask';
    case 'bpmn:ServiceTask': return 'serviceTask';
    case 'bpmn:ExclusiveGateway': return 'exclusiveGateway';
    default: return 'genericNode';
  }
}

7.2 CMMN Adapter Plan

  • cmmn-moddle maps cmmn:PlanItem definitions (Human Task, Milestone, Stage) to canvas nodes; stages render as React Flow group nodes containing children.
  • Sentries serialize as diamond nodes attached to plan item borders; entry/exit criteria become typed edges carrying onPart (event trigger) and ifPart (condition) data.
  • Discretionary items and planning tables are out of scope for v1.

7.3 DMN Adapter Plan

  • DMN bypasses the node canvas: decision tables edit exclusively in the TanStack grid.
  • dmn-moddle serializes hit policy, input/output clauses, and FEEL unary tests per rule row into DMN 1.3 XML.
  • DRD (decision requirements diagram) support deferred; v1 targets single decision tables invoked from BPMN Business Rule Tasks via decisionRef.

8. Specification Element Support

BPMN 2.0 (ISO 19510, maintained by the OMG) defines four element categories: Flow Objects (events, activities, gateways), Connecting Objects (sequence flows, message flows, associations), Swimlanes (pools, lanes), and Artifacts (data objects, groups, text annotations). The Designer covers all four categories; executable semantics target Flowable Core. v1 scope is private executable processes — collaboration and choreography diagrams render on import but multi-pool execution is out of scope.

Specification Element Type Canvas Node Identifier Configurable Engine Parameters
BPMN 2.0 Service Task serviceTask Spring Bean Delegate, Expression, Class Name, Retries
BPMN 2.0 User Task userTask Assignee Expression, Candidate Groups, Form Key (JSON Schema ref)
BPMN 2.0 Exclusive Gateway exclusiveGateway JUEL Sequence Flow Conditions (${amount > 1000})
BPMN 2.0 Business Rule Task businessRuleTask Decision Ref (DMN table), Result Variable
BPMN 2.0 Intermediate / Boundary Events intermediateEvent, boundaryEvent Timer (cron/duration), Message, Signal, Error definitions; interrupting flag on boundary events
BPMN 2.0 Sub-Process / Call Activity subProcess, callActivity Embedded (collapsible group node) vs Called Element (definition key ref), in/out variable mappings
BPMN 2.0 Parallel / Inclusive Gateways parallelGateway, inclusiveGateway Fork/join semantics; inclusive condition coverage validated by the evaluator
BPMN 2.0 Pool / Lane (Swimlanes) pool, lane React Flow group nodes; lanes map to candidate group defaults for contained user tasks
BPMN 2.0 Message Flow / Association messageFlow (dashed), association (dotted) Message flows between pools (render + interchange); associations bind artifacts to elements
BPMN 2.0 Artifacts dataObject, group, textAnnotation Non-executing context elements; preserved in XML interchange, excluded from execution validation
CMMN 1.1 Human Task cmmnHumanTask Blocking flag, Manual Activation Rule, Repetition Rule
CMMN 1.1 Sentry (On/If Part) cmmnSentry On-Event Trigger, Entry/Exit Criterion Condition
DMN 1.3 Decision Table dmnDecisionTable Hit Policy (UNIQUE, FIRST, COLLECT), Input/Output FEEL clauses

13. Dynamic Form Builder & Runtime Rendering

Forms are plain JSON Schema (draft 2020-12) stored in form_schemas, decoupled from Flowable's proprietary form format. The Designer edits schemas with a live preview; the Task Workbench renders them at runtime.

  • Binding: User Task formKey = form_schemas.form_key. The wrapper returns the formKey with each task; the SPA fetches the schema from PostgreSQL (RLS-scoped).
  • Rendering: Schema-driven renderer maps JSON Schema types to Shadcn inputs (string to text/select via enum, number to numeric input, boolean to switch, format: date to date picker). ui:* vendor extensions control layout, ordering, and widget overrides.
  • Validation: AJV validates client-side before submit; values post to /tasks/{id}/complete as process variables. The wrapper re-validates against the same schema server-side.
  • Versioning: Schemas are versioned; a deployed workflow version pins the schema version current at deploy time so in-flight tasks render the form they were designed with.

      data: {
        ...node.data,
        executionState: isActive ? 'ACTIVE' : isCompleted ? 'COMPLETED' : 'IDLE',
      },
    };
  });

16. Production Hardening & Scale Concerns

16.1 Dynamic Script Execution & Security Sandboxing

Risk

Flowable allows custom expressions (JUEL, Groovy, JavaScript) inside process gateways and service tasks. A malicious tenant developer could write a script that accesses the host container environment.

Mitigation: strict execution isolation.

  • Disable raw Groovy/JavaScript script tasks at the engine configuration level. The Designer palette excludes Script Task entirely; the wrapper's server-side validation rejects any deployment XML containing scriptTask or script listeners.
  • Expression evaluation runs in a restricted JUEL context: an allowlist of resolvable beans and variable scopes, no reflection access, no static class references.
  • If scripted logic becomes a requirement, execute it inside an isolated GraalVM sandbox (separate context per evaluation, CPU/memory limits, no host interop) rather than the engine JVM.

16.2 Process Versioning & Schema Evolution

Hosting 1,000+ workflows across 50+ tenant apps means definitions change constantly. Two guarantees:

  • Version pinning: Running process instances finish on the XML version they started with unless explicitly migrated. Flowable's native definition versioning provides this; the PostgreSQL deployments table tracks which version each instance cohort runs on.
  • Instance migration: A Process Instance Migration Engine in the wrapper uses Flowable's ProcessInstanceMigrationBuilder to transition active instances between versions without losing variable state.
public void migrateInstances(String tenantId, String sourceDefId, String targetDefId) {
    ProcessInstanceMigrationBuilder migration = runtimeService
        .createProcessInstanceMigrationBuilder()
        .migrateToProcessDefinition(targetDefId)
        // explicit activity mappings where the graph changed shape
        .addActivityMigrationMapping(
            ActivityMigrationMapping.createMappingFor("approveTask_v1", "approveTask_v2"));

    runtimeService.createProcessInstanceQuery()
        .processDefinitionId(sourceDefId)
        .processInstanceTenantId(tenantId)
        .list()
        .forEach(pi -> migration.migrate(pi.getId()));
}

Migration runs are recorded per tenant (dry-run validation via validateMigration first), and surfaced in the Designer as a version transition report.

16.3 Concurrency & Optimistic Locking Handling

At scale, concurrent API calls and async job executors mutate the same process instance, throwing FlowableOptimisticLockingException. The wrapper wraps all state-mutating operations in an automated Spring Retry aspect with exponential backoff:

@Retryable(
    retryFor = { FlowableOptimisticLockingException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 100, multiplier = 2.0)
)
public void completeTaskWithRetry(String taskId, Map<String, Object> variables) {
    taskService.complete(taskId, variables);
}
  • Applied uniformly to task completion, variable updates, signal/message correlation, and migration operations.
  • Retries are idempotency-aware: completion of an already-completed task maps to a 409 response, not a retry loop.
  • Exhausted retries emit a structured error with correlation ID for tracing (16.4).

16.4 Multi-Tenant Observability & Distributed Tracing

Tracing an execution path across Nginx, the Spring Boot wrapper, Flowable Core, PostgreSQL, and external services is vital for tenant-level diagnostics.

  • Instrument the wrapper with OpenTelemetry / Micrometer Tracing; export to the standard OTLP collector.
  • Propagate X-Correlation-ID and X-Tenant-ID headers across all REST calls, Kafka events, and async job executions.
  • Bind both IDs into the logging MDC so every log line is tenant-attributable and trace-joinable.
  • Span attributes include tenant.id, workflow.definition.key, process.instance.id, and task.id, enabling per-tenant latency and error dashboards without log scraping.

21.4 Design-Time Approval Workflow

Lifecycle extended: draft → pending_approval → approved (rejection returns a workflow to draft). The workflows.status check constraint was widened to include the two new values. Consistency between the audit trail and workflows.status is enforced by a database trigger, sync_workflow_status_from_approval, rather than two separate client writes that could partially fail: inserting a request flips the workflow to pending_approval; deciding it flips to approved or back to draft, atomically, server-side. RLS on approval_requests: any tenant member can read, designer/admin can insert (submit), only admin can update (decide).

Client-side: a Submit for Approval button appears in the Designer editor toolbar whenever the open workflow's status is draft and a version has been saved; ApprovalsPage.tsx lists every tenant's pending requests with Approve/Reject actions and an optional comment.

23. Flowable Integration Roadmap (Proposed)

Proposed August 3, 2026, alongside Workbench.html/Onboarding.html/Governance.html's counterpart sections and the new WorkflowWrapper.html, which owns the shared backend architecture (Runtime Gateway, Java 21 / Spring Boot 4, tech stack decision, Flowable/Spring Boot 4 compatibility -- resolved, see WorkflowWrapper.html Section 4) referenced throughout this section rather than repeated here. Design phase only, except where an update callout below says otherwise (23.1 and 23.3 have real, built pieces); see WorkflowWrapper.html Section 9 for the actual phase ordering across all four components.

23.1 App Packaging (.bar / .zip)

Today, BPMN/CMMN/DMN definitions are authored and exported as individual XML files (Section 21.1) -- there's no concept of a deployable unit that bundles a CMMN case, the BPMN process it calls, and the DMN table that process evaluates. Proposed: an "App Packaging" container in the Designer canvas letting a modeler group inter-dependent artifacts and produce a single archive, mirroring Flowable's own App Definition (FlowApps) concept. This is what POST /runtime/deployments (WorkflowWrapper.html Section 8) actually receives once 23.3 is built -- today that endpoint accepts a deployment request with no real packaging behind it yet.

Update, August 3, 2026: Single-Artifact Manifest Built, Not True App Packaging

The Runtime Gateway's POST /runtime/deployments now accepts a real manifest array (one packaged artifact per entry: definitionKey, name, specType, xml), and the Publish button (23.3) sends the current workflow's serialized XML as a single-entry manifest. This is not the grouping/bundling UI described above -- there is still no canvas concept of inter-dependent artifacts, and Publish only ever packages the one workflow being edited. The manifest shape was deliberately built as a list so that true multi-artifact bundling is a Designer frontend change later, not another Runtime Gateway API version.

23.2 Native Form & Data Object Modeling

Flowable's UserTask/HumanTask nodes render forms from JSON form definitions at runtime, and reference data object schemas for structured payloads. Today, PropertiesPanel.tsx lets a modeler set a plain formKey string (Section 5, node data model) with nothing behind it -- form_schemas exists in the design-time schema (Section 3) but has no editor. Proposed: a visual Form Builder (drag-and-drop fields, validation rules, visibility expressions) and a Data Object Schema Editor in the Designer canvas, persisting to the Runtime Gateway's runtime.form_definitions (WorkflowWrapper.html Section 8) rather than the existing public.form_schemas table, since the shape Flowable actually needs (field-level JSON Schema plus expression bindings) is materially different from the placeholder json_schema column that table has today.

Update, August 3, 2026: The Target API Changed

This was scoped against Flowable's standalone Form Engine (a separate, independently versioned FormRepositoryService) -- that engine was deprecated as of Flowable 7.0.1 and isn't part of Flowable 8.0.0's flowable-spring-boot-starter (confirmed while re-researching WorkflowWrapper.html Section 4). Flowable 8's actual form mechanism is the Process/CMMN engine's own FormService, tied directly to a process/case definition's embedded form key rather than an independently browsable repository. This section needs a redesign against that real API before it's buildable as described -- not a small adjustment, since "an independently versioned, Designer-authored form repository" may not be how Flowable 8 wants this to work at all. Revisit before starting Phase 3 (WorkflowWrapper.html Section 9).

23.3 One-Click Deploy

Today, Submit for Approval (Section 21.4) and Export (Section 21.1) are the only two things that happen to a saved version -- there is no path from an approved workflow to anything actually running. Proposed: once a version reaches approved status, a Publish action calls the Runtime Gateway's POST /runtime/deployments directly, closing the gap between "approved in PostgreSQL" and "deployed to a runtime." Per Governance.html's new Separation-of-Duties enforcer section, this action itself needs its own authorization check distinct from who can author or approve -- deploy authority is a third, explicit grant, not implied by either.

Update, August 3, 2026: Built

A Publish button now appears in DesignerPage.tsx's editor toolbar when a workflow's status is approved, visible only to tenant_admin accounts (canDeploy, Governance.html Section 11.3's provisional deploy-authority rule -- everyone else sees "Approved -- awaiting publish by a tenant admin" instead of a button that would just 403). It serializes the current model and calls the Runtime Gateway via a new lib/runtimeGatewayClient.ts/data/deployments.ts pair, attaching the same session JWT used everywhere else in the app (WorkflowWrapper.html Section 7's "Single Token, Two Planes"). If VITE_RUNTIME_GATEWAY_URL isn't set (true today -- the gateway hasn't been deployed anywhere, see WorkflowWrapper.html Section 0), Publish shows a clear "not configured" message rather than a confusing network error. Verified with tsc -b (zero type errors); a full vite build/oxlint pass could not run in this session's sandbox due to missing native bindings for this CPU architecture (lightningcss/oxlint's Linux ARM64 binaries), unrelated to this change -- worth a real build/lint pass before merging.
