0. How to Use This Document

This is the single entry point for developers. It explains the whole platform and links to the component design documents for depth. If you are new, read Sections 1–4, run the stack, then work through Section 11. If you are changing something, read the section for that component, Section 7 (security) and Section 13 (conventions) first.

Keep This Document True

Every change that alters how the platform works, runs or is tested updates this document and the relevant component document in the same commit. A statement here that no longer matches the code is a bug.

1. The Platform at a Glance

The Common Workflow Platform (CWP) lets organisations (tenants) design, govern and run workflows in three OMG notations: BPMN processes, CMMN cases and DMN decision tables. Designers author workflows in the browser, optionally with an AI assistant; approvers approve them; tenant admins publish them to a Flowable engine; operators watch them run. Every tenant’s data is isolated by row-level security.

2. Architecture

The browser talks to two backends. Supabase (hosted) provides identity (Auth, JWTs), the design-time database with row-level security, and two Edge Functions. CWP’s own services run in Docker Compose behind one nginx gateway. Every service verifies the Supabase JWT itself.

Principles

  • One login, many planes: the Supabase JWT authorizes Postgres RLS and every CWP service. Tenant id and role come from app_metadata.
  • The gateway routes; services decide: nginx does not validate tokens (open-source nginx can’t check JWKS signatures); each service does.
  • Database per service: workflow-runtime and spend-tracker each own a Postgres; design-time data stays in Supabase.
  • The model proposes, code decides: AI output is typed, validated and shown for review before anything changes; saving and approvals are untouched (Section 9).

4. Getting Started

Prerequisites

  • Docker Desktop (Compose v2); Node 22+ and npm; Python 3.12+ with uv; Java 21 and Maven (only to build workflow-runtime outside Docker).
  • A Supabase account on the project, with app_metadata.tenant_id and app_metadata.role set.
  • At least one AI provider key (Gemini recommended; Section 5).

First run

cd CommonWorkflowPlatform
cp .env.example .env                # fill in: passwords (any value locally), SUPABASE_*, provider keys
cp Designer/.env.example Designer/.env.local   # VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY
docker compose up -d --build        # gateway, workflow-runtime, runtime-db, agentic-designer, spend-tracker, spend-db
open http://localhost:8080          # or http://localhost:$GATEWAY_PORT (8088 on this machine)

6. Components in Depth

6.1 Designer (web app)

  • Routes: /designer, /onboarding, /workbench, /workflow-wrapper, /agentic-designer (redirects to /designer: the Agentic Designer is the Designer’s built-in AI Designer panel, with no sidebar item of its own), /admin (tenant_admin), /approvals (tenant_admin, approver), /spend (tenant_admin; platform admins see everything).
  • Canvas model: React Flow nodes and edges in a zustand store with undo/redo (zundo). BPMN and CMMN are canvases; DMN is a table editor. Saved as workflow_versions.graph_json plus generated XML.
  • Talks to: Supabase directly (auth, design-time data, Edge Functions) and CWP services via src/lib/apiClient.ts (apiFetch, and apiStream for server-sent events, which skips keepalive comments).
  • AI Designer panel (toolbar button, for designers and tenant admins): Generate, Edit and Review tabs for all three notations (Section 6.4).
  • Fixed September 27: opening a saved workflow no longer shows “Unsaved changes”; only changes that alter what is saved mark the workflow as changed (not React Flow’s size measurements or clicks).

6.2 Edge gateway

nginx serves the built SPA (deep links fall back to index.html) and routes /api/runtime/** → workflow-runtime /runtime/**, /api/agent/** → agentic-designer, /api/spend/** → spend-tracker; /api/spend/events is blocked (internal only). It answers CORS preflights itself, rate-limits per IP (20 req/s for runtime and spend, 2 req/s for agent), passes or mints X-Request-Id, logs JSON, and streams agent responses unbuffered. Upstreams resolve per request, so the gateway starts even if a service is down (that route returns 502). Details: Services.html.

6.3 workflow-runtime (Flowable)

Java 21 / Spring Boot 4 / Flowable 8 in services/workflow-runtime, with its own Postgres (runtime-db) holding the runtime schema (Liquibase) and Flowable’s engine tables. Endpoints: POST/GET /runtime/deployments, GET /runtime/deployments/{id}, GET /runtime/case-instances, GET /runtime/history/task-instances, GET /runtime/form-definitions/{id} (still a stub). Deploying is tenant_admin-only. First compiled and booted September 27, 2026 after five fixes, including a real bug where user roles were never mapped. Details: WorkflowWrapper.html.

6.4 agentic-designer (AI)

ModeEndpointWhat comes back
GeneratePOST /generate {spec, description, workflowId?}A validated model for the canvas (BPMN/CMMN) or tables (DMN)
EditPOST /edit {spec, instruction, graph, workflowId?}BPMN: patch operations; CMMN/DMN: the full updated model; plus a code-computed diff. Rejected only for errors the edit introduces
ReviewPOST /review {spec, graph, focus?}Code checks first, then grounded AI findings in fixed categories; checks-only without a model
  • Streaming: server-sent events grounding (which tenant workflows were used), attempt, invalid, result / failed, error, with 15 s keepalives.
  • Contracts and validators: graph.py (BPMN, rules AD001–AD017), cmmn.py (CD001–CD011), dmn.py (DM001–DM012), tied together per notation in specs.py. They mirror the Designer’s adapters and are anchored on the Designer’s own sample files.
  • Repair loop: up to 3 attempts; validator codes and ids go back to the model; empty replies are retried.
  • Providers: Gemini (the app’s provider), NVIDIA and OpenRouter (OpenAI-compatible). Provider errors reach users as plain messages (quota, out of credit).
  • Grounding: Section 9 and AgenticDesigner.html Section 4e.

6.5 spend-tracker

  • Endpoints: GET /summary (tenant_admin: own tenant; platform admins: all), GET /keys, POST /keys/check, GET /budgets, PUT/DELETE /budgets/{subject}, GET /alerts, POST /alerts/{id}/ack (platform admins), POST /events (services only, internal network).
  • Metering: every AI call (features generate, edit, review, embed) records tokens, estimated cost from a dated price table (prices.json; unpriced, never $0, when unknown), outcome and request id.
  • Key health: free read-only checks hourly; a key whose check says valid but whose last real call was refused is shown as “Rate-limited”.
  • Alerts: budget thresholds (80%/100%, once a month), expired/invalid keys, refused calls (including out-of-credit), low provider credit. Key alerts clear themselves when the problem goes away. Shown on the API Spend page and in the log; no email/Slack yet.

7. Security Model

ConcernHow it is handled
Tenant isolationRow-level security on every design-time table, via current_tenant_id() from the JWT. Services add their own tenant scoping (workflow-runtime in code; spend-tracker in SQL; agentic-designer reads Supabase as the user, so RLS applies). Verified live for workflow_embeddings with rolled-back synthetic tenants.
AuthenticationSupabase JWT (ES256, JWKS) checked by every service; nginx only routes.
AuthorizationRoles in app_metadata.role: designer, tenant_admin, approver, viewer. AI authoring: designer and tenant_admin. Deploy: tenant_admin. Platform-wide spend and key health: user ids in SPEND_ADMIN_USER_IDS (stand-in for a platform role).
Service-to-serviceUsage ingest requires X-Ingest-Token and is unreachable through the gateway.
SecretsOnly in .env (gitignored, mode 600). Keys go in headers, never URLs. Each service receives only the keys it needs. The spend tracker stores key names, never values.
AI safetyUser text, tenant workflows and model output are fenced as data in prompts; model output is schema-checked and validated before use; nothing the AI returns is saved or deployed without a person; review findings are grounded in real ids. Only sizes and outcomes are logged, never prompts.
Anonymous accessRevoked on workflow_embeddings; the search function is executable by authenticated users only.

9. How the AI Parts Are Built

  1. Typed contracts per notation that mirror the Designer’s adapters. Unknown fields are rejected, not dropped.
  2. Validators decide whether a proposal is acceptable; stable rule codes go back to the model to repair.
  3. People decide whether a change is applied: previews with highlights, Accept/Reject, then the normal save and approval flow.
  4. Grounding shows the model condensed summaries of the tenant’s most similar workflows (pgvector search in Supabase, read as the user; embeddings written lazily; best-effort). Measured effect: the tenant’s own names appear when grounded (Kimi 3/3 vs 0/3; Gemini 2/3 vs 1/3).
  5. Everything is measured: every call metered; an evaluation harness scores providers on 22 cases, judging DMN by executing the tables.

11. Manual Test Plan (Do This Yourself)

These need a real login and so can’t be automated here. Work through them in order at http://localhost:8088 after docker compose up -d --build. Tick each expected result; anything different is a bug worth a note with the time (for the logs) and a screenshot.

A. Stack health (2 minutes)

  1. docker compose ps: gateway, workflow-runtime, runtime-db, agentic-designer, spend-tracker, spend-db all Up. → All six running.
  2. Open http://localhost:8088/api/agent/healthz. → {"status":"ok","provider":"gemini"}
  3. Run cd services/agentic-designer && uv run python scripts/check_gemini.py. → Both models OK.

B. Sign in and the Designer

  1. Sign in. → You land in the Designer; your tenant and role show in the header.
  2. Open an existing workflow. → No “Unsaved changes” until you actually change something (fixed today).
  3. Drag a node. → “Unsaved changes” appears. Save Version. → “Saved”.

C. AI Designer: BPMN

  1. Create a new BPMN workflow, click AI Designer → Generate, describe a loan approval (“an underwriter reviews; over 10,000 needs a manager; then the system pays out”). → Within ~10 s a laid-out process appears; “Unsaved changes” shows.
  2. If you already have similar saved workflows: → the panel says “Following the conventions of your workflow …”, and the result reuses their group names.
  3. Edit tab: “Loans over 50,000 also need a compliance review after the manager approval.” → New items outlined green, changes listed in words. Click Reject → canvas exactly as before. Repeat and Accept → highlights go, changes stay.
  4. Review tab, Review. → Findings grouped as Problems / Warnings / Suggestions, labelled Check or AI; clicking one selects its nodes.
  5. Save Version, then Submit for Approval. → Status becomes pending approval.

D. AI Designer: CMMN and DMN

  1. New CMMN workflow → Generate a fraud investigation case. → Human tasks, milestones and sentries on the canvas. Edit: “legal must review before the decision” → links described as (on complete) / (entry).
  2. New DMN workflow → Generate a loan risk tier from credit score and debt-to-income. → A decision table appears in the table editor. Edit: add a rule → the change list (“added rule N”) shows; the table only changes after Accept.
  3. Import Designer/samples/investigation-decisions.dmn, Review it. → AI findings include the PRIORITY hit policy with no output ordering, and a department no rule covers.

E. Governance and runtime

  1. As an approver (another account), approve the workflow from C.5. → Status approved.
  2. As a tenant_admin, open it and click Publish. → “Deployment created”. Then Workflow Wrapper page → the deployment is listed. (Publish through the gateway has not yet been tested with a real login.)
  3. As a viewer: → no AI Designer button; AI endpoints refuse (403).

F. API Spend

  1. As a platform admin (your id is in SPEND_ADMIN_USER_IDS) open API Spend. → “Platform-wide” badge; this month’s calls from sections C–D appear with Gemini costs; unpriced NVIDIA calls counted separately.
  2. Key health. → Gemini OK (its old refused-call alert clears after a successful call), NVIDIA OK, OpenRouter OK, TypeSafe OK. Click Check now → times update.
  3. Set a tiny Gemini budget (e.g. $0.01). → Near/over-budget alerts appear immediately. Dismiss them, then set a realistic budget (e.g. $10).
  4. As a tenant_admin who is not a platform admin. → “Your tenant” only; key health says platform admins only.

13. Conventions

  • Git: imperative, present-tense commit subjects; stage specific paths, never git add .; never push without an explicit request; never force-push main. Your own unrelated work in progress stays out of commits.
  • Code: match the surrounding style; smallest change that solves the problem; no speculative features; comments explain why. Python via uv; TypeScript strict and lint-clean.
  • Tests: encode intent; a fixture breaks exactly one thing; run mutation checks on new logic.
  • AI: the model proposes, code decides, a person accepts; use the model only for judgement calls; fence untrusted text; meter every call.
  • Data: additive, clearly named migrations on the shared Supabase project; keep the portable scripts in step; test RLS with rolled-back synthetic data.
  • Docs: update this manifesto and the component document in the same commit as the change (Section 0).
  • Secrets: never print, log or commit a key; copy them between env files with scripts that don’t display values.

15. Known Limits & What’s Next

  • Not yet tested with a real login: the browser flows in Section 11, including Publish through the gateway and grounding end to end. The first real login (September 27) showed the project signs logins with HS256; every earlier check used test tokens signed with the JWKS key, which is why it wasn’t caught sooner.
  • workflow-runtime has no automated tests, including none for tenant isolation (a known risk).
  • Deploying AI-made CMMN or DMN models through Publish to Flowable is untested.
  • Alerts show in the app and log only; email or Slack needs a channel choice.
  • No platform-level role yet; SPEND_ADMIN_USER_IDS stands in.
  • Mobile: the app shell’s fixed sidebar isn’t built for phones.
  • Form rendering (/runtime/form-definitions) is a stub pending a redesign.
  • Rate limits are per process (one replica); move to a shared store before scaling out.
