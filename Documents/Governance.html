0. Decision Summary

The Administration and Approvals screens built in the last session work, but the role model underneath them is deliberately minimal: three flat, mutually exclusive, tenant-scoped roles (designer, admin, viewer). That was the right call to ship something real quickly. It is not the right long-term model for a platform meant to govern workflow changes across an organization. This document brainstorms what the model should grow into, and in what order -- no schema or code changes are made here.

Central Tension

Today's admin role bundles three genuinely different kinds of authority into one claim: managing who's on the team, deciding whether a workflow change is safe to publish, and having full designer edit rights. A tenant admin, a compliance approver, and a power-user designer are not the same job, and treating them as one role means every admin has to be trusted with all three, whether or not that's appropriate for the organization using this platform.

2. What's Wrong With The Flat Model

Six concrete gaps, roughly in order of how much they'd matter to a real organization adopting this platform:

  • No separation of duties. An admin can author a workflow, submit it for approval, and approve their own submission. There is nothing in the RLS or the trigger stopping this today.
  • Approval authority is bundled with tenant administration. Organizations commonly want a compliance or risk officer to approve workflow changes without that same person being able to delete workflows or reassign everyone else's roles. Today that's impossible -- approval power only comes with full admin power.
  • No cross-tenant oversight. If WaaS operates this as a multi-tenant platform for multiple business units or clients, there is currently no way for a platform-level team to audit or support a tenant without directly querying the database. Every tenant is an island, including from the platform operator's own view.
  • No real audit trail. approval_requests covers approval decisions, but role changes, deletes, and archives leave no record. If a workflow disappears, there's no way to answer "who did that and when" from inside the app.
  • No invite or offboarding flow. Growing a team means someone has to be manually bootstrapped into profiles/auth.users via direct SQL (as was done twice already in this project). There's also no way to deactivate a departing user short of deleting their row outright.
  • No delegation. If the only approver for a tenant is unavailable, nothing can move from pending_approval to approved. Single point of failure by construction.

Status as of August 3, 2026: the first four gaps are closed (Phases 1–4, Section 10). Delegation and cross-tenant oversight remain open (Phases 5–6).

3. Proposed Role Model

Two axes, deliberately separated: platform-level (who WaaS itself trusts across every tenant) and tenant-level (who a given organization trusts within its own workspace). Today only the tenant axis exists.

3.1 Platform-Level Roles

New concept, doesn't exist today. A single role, platform_superadmin, held by WaaS's own operators (not by tenant users). Its purpose is narrow: cross-tenant read access for support and audit, never a silent bypass of tenant RLS for writes. Two implementation directions worth weighing later, not decided here:

  • An entirely separate internal tool (its own auth, its own service-role-backed read path) that never shares a login surface with the tenant-facing app -- safer by construction, more to build and operate.
  • A platform_superadmin claim recognized by an additional, explicitly audited RLS policy on each table (current_role_claim() = 'platform_superadmin' OR the existing tenant check) -- less to build, but every table's RLS becomes a place this claim has to be remembered and reasoned about.

Leaning toward the separate tool for anything that touches real tenant data, and reserving the shared-login approach only for read-only aggregate views (e.g., "how many tenants are on the platform" style operational dashboards) that never need row-level tenant data.

3.2 Tenant-Level Roles

Refined from three to four concepts -- three of which map directly onto today's roles, plus a genuinely new one:

RoleRelation To TodayScope
tenant_adminNarrowed from today's adminUser/role management, tenant settings, delete/archive any workflow. Does not automatically include approval authority.
approverNew -- currently bundled into adminCan decide pending approval requests. Nothing else beyond what their other capabilities grant.
designerUnchangedAuthor, edit, save, export, submit for approval.
viewerUnchangedRead-only.

The open design question is whether a person can hold more than one of these at once -- e.g., a designer who is also an approver for a different team's submissions. That's addressed directly in 3.3, because the answer changes the schema shape.

3.3 Role vs. Capability: Which Model?

Two candidate directions, not a decision yet:

Option A -- Add a role value

Extend the existing single-role-per-user pattern: role becomes one of designer / tenant_admin / approver / viewer. Minimal change to the current schema and RLS shape. The real limitation: a user still can't be both a designer and an approver, which is a common real-world need (a senior engineer who authors most workflows but is also trusted to approve others' work).

Option B -- Move to a capabilities model (recommended direction)

Replace the single role text column with a capabilities text[] array (or a join table if capabilities need their own metadata later): a user can hold ['author'], ['author', 'approve'], ['administer'], any combination. RLS policies check 'approve' = any(current_capabilities()) instead of current_role_claim() = 'admin'. More flexible and closer to how real organizations actually assign responsibility, at the cost of a real migration: every existing RLS policy that reads current_role_claim() would need to be rewritten, and the JWT claim shape changes from a string to an array.

Recommendation: stay with Option A (add approver as a fourth role value) for the first iteration, since it's a small, low-risk change on top of a pattern that's already proven to work, and revisit Option B only if "one person needs multiple capabilities" turns out to be a real recurring need once there are actual multi-role users to observe.

4. Segregation Of Duties

Independent of which role model wins, one rule is cheap to add and closes a real gap immediately: a user should never be able to decide their own approval request. Two enforcement points to consider together, not either/or:

  • RLS check on the approval_requests "admin decide" policy: add requested_by is distinct from current_user_id() to the USING clause, so the database itself refuses the update regardless of what the UI allows.
  • UI check in ApprovalsPage.tsx: hide or disable the Approve/Reject buttons on a request the current user submitted themselves, so the restriction is visible before someone hits an error.

Stretch idea, not required for a first pass: configurable per-tenant policy for whether certain spec types (e.g., DMN decisions with sanction-severity outputs) require two distinct approvers rather than one, mirroring real compliance sign-off patterns. This would need its own small table (approval_policy: tenant_id, spec_type, required_approvals int) and a trigger change to only flip workflows.status to approved once the count is met.

5. Cross-Tenant Governance

"Governance among the tenants" cuts two ways, worth naming separately since they have different answers:

  • Tenant-to-tenant isolation (should stay exactly as strict as it is today): every tenant-scoped RLS policy remains keyed on current_tenant_id(); nothing in this document proposes loosening that. Tenants should never be able to see each other's workflows, members, or approval history.
  • Platform-to-tenant oversight (the actual gap): the WaaS platform team currently has no supported way to look across tenants for support, compliance, or capacity questions without dropping into raw SQL against the database directly, which is both risky (no audit trail on those reads) and slow. This is what platform_superadmin in 3.1 is meant to solve, deliberately kept read-oriented and, ideally, built as a separate tool from the tenant-facing app rather than a hidden mode inside it.

7. Audit Log Design

A single generic table rather than one bespoke log per feature, so Administration only needs one "Audit Log" tab regardless of how many things get logged over time:

ColumnPurpose
tenant_idScopes every read the same way every other table already does
actor_idWho performed the action
actionShort code, e.g. role_changed, workflow_deleted, workflow_archived, approval_decided
entity_type / entity_idWhat was acted on (a workflow, a profile, a request)
before / after (jsonb)Snapshot of the changed fields, for a real diff view later
occurred_atTimestamp

Population strategy: database triggers on the tables that matter (profiles role changes, workflows deletes/archives, approval_requests decisions), the same pattern already proven with sync_workflow_status_from_approval -- so this is additive to something already working, not a new pattern to invent.

8. Invite & Deactivate Flow

Shares its data model with Onboarding.html's invite design (cross-reference: Onboarding.html Section 4) -- listed here too because it's equally a governance concern (who gets let into a tenant, and how they get removed).

  • Invite: an invites table (email, tenant_id, role, invited_by, status, token, expires_at) plus a serverless function using the auth service's admin invite-by-email API, the same service-role pattern already proven with admin-set-role.
  • Deactivate: add a profiles.status column (active / deactivated) instead of deleting the row outright -- preserves the audit trail (a deactivated user's past approvals and authored workflows should still show correctly attributed) while an RLS check on write-granting policies excludes deactivated users going forward.

9. Approval Delegation

Addresses the single-point-of-failure gap from Section 2: if the only approver is out, nothing moves. Sketch of a delegation model, not a final design: an approval_delegations table (tenant_id, from_user_id, to_user_id, starts_at, ends_at). When listing who can decide a pending request, the Approvals query would include both direct approvers and anyone currently delegated to by an approver. Kept as its own phase (see Section 10) since it depends on the approver role existing first.

11. Flowable Integration Roadmap (Proposed)

Proposed August 3, 2026. Extends this document's own Sections 3-8 with three items that specifically need Flowable-shaped capability -- deployment-target inheritance, engine-native history, and a deploy-time SoD check. See WorkflowWrapper.html Section 9 for how these map onto that document's phase numbering (11.1 is Phase 5; 11.2 is Phase 9; 11.3 is Phase 4, notably not blocked on Flowable itself and startable as soon as Phase 1's deploy endpoint exists).

11.1 Multi-Tenant Deployment Target Mapping & Shared Artifacts

Flowable's own multi-tenancy model supports a default-tenant inheritance pattern: definitions deployed without a specific tenant ID act as a fallback template every tenant can use unless a tenant deploys its own override. Proposed: platform-level platform_superadmin (Section 3.1, not yet built) or, in the interim, a designated tenant, deploys Global Workflow Templates to a default namespace via the Runtime Gateway; tenant admins choose per-template whether to inherit the global version or override it with a tenant-specific definition. This is a natural extension of Onboarding.html Section 7.1's tenant-aware seed bundles -- the seed bundles are the first consumers of whatever a "global template" ends up meaning here.

11.2 Comprehensive Engine Audit Logging & History Level

Section 7's audit_logs table (built) covers role/status changes, workflow archive/delete, and approval decisions -- everything happening on the database side. It has no visibility into what happens once something actually runs. Proposed: once a real Flowable engine exists (WorkflowWrapper.html Phase 7), feed its native history endpoints (historic-task-instances, historic-activity-instances) into the same audit_logs table via a new action family (e.g. task_completed, activity_reached), so Administration's Audit Log tab (built, Designer.html Section 22.1) stays the one place to look regardless of whether an event happened at design time or run time -- rather than a second, separate log UI.

Update, August 3, 2026: The Blocker Is Gone, The Wiring Still Isn't Built

WorkflowWrapper.html Phase 7 is done -- Flowable 8.0.0 is embedded in the Runtime Gateway and its real HistoryService is queryable (WorkflowWrapper.html Section 5, backing GET /runtime/history/task-instances). That resolves the "once a real Flowable engine exists" precondition above. What's still missing is the second half: nothing yet writes those historic events into audit_logs -- the Runtime Gateway exposes history as its own read endpoint, but doesn't push into the PostgreSQL database. That plumbing (a new action family, and either a webhook/serverless-function push from the gateway or a polling job) is still unbuilt.

11.3 Explicit Separation Of Duties (SoD) Enforcer

Flowable itself distinguishes deployment authorization (/repository/deployments) from runtime task-execution permissions -- they're never the same grant. Proposed, and buildable now rather than blocked on Flowable (WorkflowWrapper.html Section 9, Phase 4): a third explicit capability, distinct from both designer (authors drafts) and approver (reviews and decides, Section 3.2, built) -- call it deploy authority -- gating who can call the Runtime Gateway's POST /runtime/deployments (Designer.html Section 23.3's one-click Publish). Whether this is a fifth role value, a capability grantable alongside approver, or folded into tenant_admin is an open design choice deferred to when Phase 4 is actually picked up -- flagged here so it isn't decided by default. The existing self-approval guard (Section 4, built: an approver can never decide their own request) is the direct precedent for how this should be enforced -- at the authorization layer the Runtime Gateway checks, not just hidden in the UI.

Update, August 3, 2026: Provisional Version Built

Phase 4 has been picked up as part of the Runtime Gateway's Phase 1 scaffold (WaaS/Workflow-Wrapper, DeploymentService.assertDeployAuthority()). The open design choice above was resolved provisionally, not definitively: deploy authority was folded into the existing tenant_admin role rather than becoming a fifth role value or a separately grantable capability -- the simplest option, chosen so Phase 1 wasn't blocked on a role-model decision. This is explicitly a placeholder: it does not yet implement the "author of this definition cannot also deploy it" check that would make this a real SoD control rather than a coarse role gate. Revisit before this matters for a real compliance boundary. Also uncompiled/unverified along with the rest of the Phase 1 scaffold -- see WorkflowWrapper.html Section 0.
