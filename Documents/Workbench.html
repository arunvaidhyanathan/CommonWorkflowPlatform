0. Decision Summary

Workbench exists as a nav entry and a placeholder route today, nothing more. This document brainstorms what should actually live there, and argues for a specific distinction that keeps it from turning into a second, redundant copy of either Designer or Administration.

Framing

Designer is where you build a workflow. Administration is where you configure who can do what. Workbench is where you start your day -- what's waiting on you, what changed recently, and a fast path into whichever of the other two screens you actually need.

1. What Workbench Is Not

Worth naming explicitly, since without a clear boundary this screen tends to accumulate scope from both directions:

  • Not a second Designer. No canvas, no palette, no editing. Workbench surfaces work; Designer does the work.
  • Not Administration. No role management, no tenant settings, no delete/archive controls. Those stay governance-scoped and admin-gated.
  • Not a duplicate of Approvals. Workbench can surface "you have approvals waiting" as a summary card, but the actual approve/reject UI stays on the dedicated Approvals screen -- one canonical place to do that action, not two.

2. Core Workbench Experience

2.1 "My Work" Dashboard

The centerpiece. A small set of cards, each answering one question at a glance:

  • My drafts -- workflows this user authored that are still in draft, with a direct link into the editor.
  • Waiting on me -- if this user holds approval authority (see Governance.html's proposed approver role), a count and list of pending requests, linking to Approvals.
  • Recently edited -- the last handful of workflows this user touched, regardless of status, for quick re-entry without hunting through the full list.
  • My submissions -- workflows this user submitted that are still pending_approval, so they can see what they're waiting on without pestering the approver.

2.2 Tenant Activity Feed

A lightweight, reverse-chronological feed of what's happened across the tenant recently -- saves, imports, submissions, approval decisions. Directly benefits from the audit log proposed in Governance.html Section 7 once it exists; until then, could be approximated from workflows.updated_at and approval_requests alone, just with less detail (no role-change or delete events visible without the real audit table).

2.3 Global Search & Filter

A single search bar across all workflows in the tenant -- by name, definition key, spec type, status, or owner -- so finding a specific workflow doesn't require scrolling the flat Designer list. This is arguably the single highest-value addition once a tenant has more than a handful of workflows; the current Designer list has no search at all.

2.4 Notifications

Start small: a badge count on the Approvals nav item (already has the data via listPendingApprovals), and a badge on Workbench itself once "waiting on me" exists. Full notification infrastructure (in-app notification center, email digests) is a much bigger feature and shouldn't be the first thing built here -- badge counts on existing screens get most of the value for a fraction of the effort.

2.5 Quick Actions

New Workflow and Import shortcuts surfaced directly on Workbench, not buried behind a click into Designer's list view first -- if Workbench becomes the landing page (see Section 3), it needs to offer the two most common actions immediately, not just a read-only dashboard.

3. The Landing-Page Question

The most consequential decision in this document, worth flagging distinctly rather than burying in the feature list: should Workbench replace Designer's current "Workflows" list view as the screen a user lands on after login, with Designer becoming purely the canvas/editor reached from Workbench?

Argument For

Today, logging in drops a user straight into a flat, unfiltered list of every workflow in the tenant, with no sense of what's relevant to them specifically. That's a reasonable default when there are three sample workflows in the whole tenant; it stops being reasonable once there are a hundred. "What should I look at first" is exactly the question Workbench is designed to answer.

Argument Against

It's a bigger structural change than it sounds -- DesignerPage.tsx's list view currently does double duty as both the workflow browser and the entry point for New/Import. Splitting that out means Workbench needs to either duplicate that browsing UI or Designer's list view needs to be demoted to something reached via a "Browse All Workflows" link from Workbench, which is more restructuring than a first pass probably needs.

Leaning toward: keep Designer's list view as-is for now, and let Workbench be an additional, complementary landing option (perhaps even the actual / redirect target instead of /designer) rather than replacing anything on day one. Revisit full consolidation once Workbench's dashboard has proven itself useful.

4. Layout Sketch

Rough composition, top to bottom

Quick actions bar (New Workflow / Import) — full width, top
Card grid (2–3 columns): My Drafts | Waiting On Me | My Submissions | Recently Edited
Search bar, full width, above a filterable table (same row shape as Administration's workflow governance table)
Activity feed — right-hand sidebar or below the fold, lower priority than the cards

Reuses existing visual language rather than inventing new components: the card style already exists in the "Getting Started" panel sketched in Onboarding.html, and the filterable table can reuse the same row shape as Administration's workflow governance table.

7. Flowable Integration Roadmap (Proposed)

Proposed August 3, 2026. All three items here are Phase 8 in WorkflowWrapper.html Section 9 -- originally deliberately last, since all three need a real Flowable engine to show real data, not the thin-layer placeholder the Runtime Gateway started as. Explicitly not what Section 1 warns against: none of this makes Workbench a second Designer (still no editing) or a second Approvals (still no decide UI) -- it's read/act-on-running-work visibility, consistent with this document's own framing.

Update, August 3, 2026: 7.1 Built (Elsewhere), 7.3 Unblocked, 7.2 Is Not

The "needs a real engine" precondition above is now true for 7.1 and 7.3 -- WorkflowWrapper.html Phase 7 embedded Flowable 8.0.0 for real, and /runtime/case-instances now queries its actual CmmnRuntimeService. 7.1's view is now built, but it lives at the /workflow-wrapper route (WorkflowWrapperPage.tsx), not inside WorkbenchPage.tsx as this section originally sketched -- see the note below for why. 7.3 is unblocked (real engine exists) but still not built -- it needs a diagram-state endpoint the Runtime Gateway doesn't have yet. 7.2 is a different story: the standalone Flowable Form Engine this section assumed doesn't exist anymore (deprecated as of Flowable 7.0.1, see WorkflowWrapper.html Section 4) -- getting a real engine wasn't the blocker for 7.2, a wrong assumption about which API to build against was. See the note on 7.2 below.

7.1 CMMN Dynamic Plan Item & Case Task Management

Today, Workbench has no case-execution concept at all -- "My Work" (Section 2.1) is entirely a design-time view over workflows/approval_requests. Once a CMMN case is actually running (WorkflowWrapper.html Phase 7, now built), case workers need visibility into which plan items are Active, Available, Enabled, or Discretionary, and a way to trigger optional/ad-hoc tasks and stage transitions. Proposed: a Case Instance View reading the Runtime Gateway's /runtime/case-instances (WorkflowWrapper.html Section 8), which itself mirrors Flowable's /cmmn-runtime/case-instances and is now backed by a real, tenant-scoped engine query.

Built, August 3, 2026 -- at a different location than sketched above. The read-only view (case instances, plus deployments and BPMN task history alongside it) landed in WorkflowWrapperPage.tsx at the pre-existing /workflow-wrapper route, not inside WorkbenchPage.tsx. That route already existed in the app shell as the reserved home for "the Runtime Gateway's operator-facing surface" (Designer.html Section 21.2); adding a second place to look for the same data would have worked against this document's own goal of consolidating scattered visibility into fewer, not more, screens. Trigger actions on plan items/stages (the "way to trigger optional/ad-hoc tasks" half of this section) are still not built -- the Runtime Gateway has no write endpoints for case execution yet, only the read-side queries described in WorkflowWrapper.html Section 8.

7.2 Dynamic Flowable Form Rendering Engine

Task completion in Flowable means submitting a payload matching the form definition attached to the task's node -- originally scoped to be exactly what Designer.html Section 23.2's Form Builder would produce, read back via a Flowable Form Engine FormRepositoryService. That target no longer exists: Flowable's standalone Form Engine was deprecated as of 7.0.1, and Flowable 8's own form handling lives in the Process/CMMN engine's built-in FormService, tied to a specific process/case definition's embedded form key rather than an independently browsable, versioned repository. This section needs a real redesign against that actual API -- not a "swap the backing" change like 7.1/7.3 got -- before it's buildable. Flagged, not silently carried forward as if nothing changed.

7.3 Real-Time Process/Case Execution Diagrams

Flowable can overlay active/completed/pending execution state directly onto the original diagram. Proposed: render the existing @xyflow/react canvas (the same one Designer already uses to author) in a read-only mode inside Workbench, with node highlighting driven by a diagram-state endpoint on the Runtime Gateway. Reuses Designer's canvas component rather than building a second rendering path -- the canvas already knows how to lay out and draw BPMN/CMMN graphs; this just adds an overlay layer and turns off editing.
