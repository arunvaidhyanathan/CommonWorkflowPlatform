0. Decision Summary

There is no onboarding today. Every tenant and every user in this project so far has been provisioned by direct SQL against Supabase, run manually. That's fine for a two-person build session; it's a dead end for anyone else who tries to sign up. This document brainstorms what a real onboarding experience should look like, split into four distinct flows that get conflated if treated as one problem.

Framing

"Onboarding" isn't one screen, it's four different moments: creating a brand-new tenant, joining an existing one, a new user's first few minutes inside the app, and what an experienced user sees when they hit an empty list. Each needs its own design, even though they'll likely share components.

1. Problem Statement

Today, a brand-new Supabase Auth user who signs up hits DesignerPage's "Workspace Not Provisioned" screen and stops there -- correct behavior given no self-serve path exists, but a genuine dead end from the user's perspective. There's no way for them to create a tenant, no way for them to ask to join one, and no way for an existing admin to bring them in without someone running SQL by hand. This is the single biggest gap between "this works for us building it" and "this works for anyone we'd hand it to."

2. The Four Onboarding Flows

2.1 New Tenant Creation

The very first user of a brand-new organization. They have no tenant, no invite, nothing to join. Proposed flow: a short form (organization name, slug) submitted through a dedicated, unauthenticated-friendly signup path; on submit, a tenant row is created and the submitting user is automatically assigned tenant_admin (per Governance.html's proposed role) for that new tenant -- they're the first person in, so they have to start as the admin. This is the one flow that unavoidably needs a privileged write (creating a tenant and setting the first user's role), so like admin-set-role, it has to be an edge function, not a direct client write.

2.2 Invite Into An Existing Tenant

The far more common case day-to-day: a tenant_admin invites a colleague. Proposed flow, shared design with Governance.html Section 8: admin enters an email and picks a role in Administration, which creates a row in a new invites table and triggers an edge function that calls supabase.auth.admin.inviteUserByEmail. The invited person gets a real email, clicks through, sets a password, and lands already provisioned -- no manual SQL, no waiting on someone else to run a query.

2.3 First-Login Guided Tour

For a freshly provisioned user (from either flow above), the first few minutes inside the app matter more than any other session they'll have. Proposed: a lightweight, dismissible tour -- not a blocking modal wizard, which people click through without reading, but a small persistent "Getting Started" panel (see 3.2) that points at real UI (the nav sidebar, the New Workflow button) rather than describing it in the abstract.

2.4 Empty-State Onboarding

Every empty list in the app is a missed onboarding opportunity today. The Designer workflow list already has a plain "No workflows yet" message -- that's the right instinct, underused. Proposed: turn every empty state into an action, not just a statement, and specifically use the sample files already sitting in Designer/samples/ (the Ethics Investigation case, the Investigation Decisions DMN) as one-click starter imports -- "Don't know where to start? Import a sample case" is a much lower-friction first action than "click New Workflow and figure out BPMN from scratch."

3. UI/UX Design Ideas

3.1 Tenant Creation: Wizard vs. Single Form

Recommend a single short form over a multi-step wizard for 2.1 -- organization name and slug is genuinely all that's required to unblock the first user, and a wizard for a two-field form would be friction for its own sake. Save the multi-step treatment for something that actually has multiple decisions to make (there isn't one here yet).

3.2 The "Getting Started" Panel

Sketch -- shown above the Workflows list until dismissed or all items checked

☐ Create your first workflow, or import a sample
☐ Invite a teammate
☐ Review the Designer basics (links to a short help doc)

Each checklist item links directly to the real action (opens the New Workflow dialog pre-filled, opens Administration's invite form, etc.) rather than to a separate help page. Dismissible per-user via a simple profiles flag or local component state; reappears for each new user in a tenant even after the tenant's first user has dismissed it, since it's about the individual's first-run state, not the tenant's.

3.3 Role Selection During Invite

The invite form shouldn't just show a bare dropdown of role names -- someone deciding "should this person be a designer or a viewer" benefits from a one-line explanation inline, e.g. next to each option in the picker: "Designer -- can create and edit workflows. Viewer -- can see workflows but not change them. Approver -- can approve or reject submitted changes." Small thing, meaningfully reduces mis-assigned roles.

3.4 Empty States As Actions, Everywhere

Beyond the Workflows list: Approvals' "Nothing pending approval right now" and Administration's "No tenant members found" are both currently just text. Approvals' empty state could point back at Designer ("Nothing to review -- see what's in Draft"); Administration's could point at the invite flow once it exists.

4. Data Model Implications

Brainstorm only, no schema decided yet -- flagging what each flow would need so Governance.html and this document stay consistent with each other (Section 8 there covers the same invite need from the administration side):

FlowNew Data Needed
2.1 New tenantNo new table -- reuses tenants + profiles, just needs an edge function to do the privileged first-write instead of direct SQL
2.2 Inviteinvites table (email, tenant_id, role, invited_by, status, token, expires_at) + an edge function using auth.admin.inviteUserByEmail
2.3 Guided tourA per-user "onboarding dismissed" flag -- could live on profiles as a boolean, or purely client-side (localStorage) if it doesn't need to persist across devices
2.4 Empty statesNo new data -- purely a UI change referencing the existing sample files

5. Open Questions & Risks

  • Self-serve tenant creation vs. admin-provisioned only? Letting anyone create a tenant is the friendliest option but means anyone can spin up an org with no gatekeeping -- worth deciding deliberately rather than defaulting into it.
  • Domain-based auto-join? Common pattern (anyone signing up with an @company.com email auto-joins that company's tenant) -- convenient, but a real security decision, not a default to make lightly.
  • Email deliverability. The invite flow depends entirely on Supabase Auth's transactional email actually landing, which needs a configured email provider in production, not just the default Supabase sender.
  • Guided tour fatigue. If it's ever made a blocking modal instead of a dismissible panel, it will get clicked through unread within a week of anyone using the product regularly -- worth resisting that direction even if it seems more "complete."

7. Flowable Integration Roadmap (Proposed)

Proposed August 3, 2026. Both items are Phase 6 in WorkflowWrapper.html Section 9 -- buildable against the invite flow and tenant model already built (Section 2.2, live), without needing a real Flowable engine, since they're about what gets provisioned alongside a new tenant/user, not about runtime execution itself.

7.1 Tenant-Aware Default App Bundles

Today, a brand-new tenant starts with an empty workflows list -- Onboarding.html Section 2.4's sample imports (built) address this one user at a time, by hand. Proposed: when a new tenant is provisioned (whether via the still-deferred self-serve tenant creation, Section 2.1/Phase 3, or the existing manual-bootstrap path), automatically deploy a standard set of starter templates -- Document Approval, Incident Management, a common Decision Matrix -- into that tenant's namespace via the Runtime Gateway, once app packaging (Designer.html Section 23.1) exists to define what a "template" actually is.

7.2 Tenant-Isolated User & Group Provisioning

The invite-user edge function (Section 2.2, built) already sets app_metadata.tenant_id/role on invite. Proposed extension once the Runtime Gateway exists: mirror that same tenant-scoped identity into the gateway's authorization model with tenant-prefixed keys (e.g. tenantA:designer), matching Flowable's own multi-tenancy convention of prefixing group IDs with a tenant key to keep identity globally unique while staying tenant-isolated. This is additive to the invite flow, not a replacement -- Supabase stays the single identity provider (CWP.html Section 2); the Runtime Gateway just needs its own tenant-safe representation of "who is this" for the runtime-shaped endpoints in WorkflowWrapper.html Section 8.
