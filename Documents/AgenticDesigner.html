0. Decision Summary

CWP.html listed the Agentic Designer as out of scope until Designer's editors matured. They have: BPMN, CMMN and DMN editing, versioning, approvals and one-click Publish all exist. This document is the design for adding an AI authoring assistant on top of them without weakening any of the governance already built.

What's Decided
  • A separate Python / FastAPI service, agentic-designer, reached through the nginx edge gateway (Services.html).
  • Provider-agnostic LLM layer. A thin LLMProvider interface with Anthropic and Gemini adapters to start; provider and model come from configuration.
  • The model never writes BPMN XML and never writes to the database. It proposes changes against a typed graph contract; code validates them; the SPA applies them to the canvas; the user saves through the existing path.
  • Agent output is always a draft. It goes through the same RLS, versioning, approval and audit flow as hand-made changes.
  • Stateless in v1. The client sends the conversation and the current graph with each request.

2. The Core Rule: The Model Proposes, Code Decides

  1. The model returns tool calls against the typed graph contract (Section 3): a whole graph for Generate, patch operations for Edit.
  2. The service validates the proposal: schema first (Pydantic), then structure (the validator rules in Section 3).
  3. If validation fails, the errors go back to the model for at most 2 repair rounds; after that the user sees the errors instead of a broken graph.
  4. The SPA converts the accepted graph into its canvas format (GraphSnapshot in Designer/src/data/workflows.ts). Every node arrives at position (0, 0), which makes the existing needsAutoLayout / applyAutoLayout (Designer/src/adapters/autoLayout.ts) lay it out. The existing BPMN adapter produces the XML on save.
  5. Saving uses the existing path, so tenant isolation, workflow_versions, approvals and audit_logs all apply unchanged.

3. Graph Contract

Built in phase A0 at services/agentic-designer/src/agentic_designer/. No LLM and no HTTP yet: this is the contract every later phase is checked against.

3.1 Graph (graph.py)

WorkflowGraph holds nodes and edges. JSON field names are camelCase so they match the SPA's NodeData exactly. Unknown fields are rejected rather than dropped, so a model inventing an attribute is caught.

ElementFieldsNotes
Nodeid, type, label, documentation, assignee, candidateGroups, delegateExpression, formKeyid must be a valid BPMN id (^[A-Za-z_][A-Za-z0-9_.-]*$)
Edgeid, source, target, label, conditionExpressionNo separate "default flow" flag: the Designer's BPMN adapter doesn't write one, so one unconditioned branch acts as the fallback

Node types: the Designer's BPMN palette (startEvent, endEvent, intermediateEvent, userTask, serviceTask, businessRuleTask, callActivity, subProcess, exclusiveGateway, parallelGateway, inclusiveGateway) minus boundaryEvent (needs a host node the canvas format can't express yet) and genericNode (the Designer's fallback for unknown elements). CMMN and DMN come in A4.

Field applicability: assignee and candidateGroups on user tasks; formKey on user tasks and start events; delegateExpression on service tasks. These match what Flowable acts on.

3.2 Patch operations (patch.py)

OpPayloadNotes
add_nodenode
update_nodeid, changesLabel and the optional fields only. Changing id or type is not allowed: that's a remove plus an add, so the node's flows get reconsidered
remove_nodeidAlso removes every flow touching the node
connectedgeBoth ends must exist
disconnectedgeId
set_conditionedgeId, conditionExpressionnull clears it

apply_patch returns a new graph and never modifies the original (so Reject restores exactly what was on the canvas). A bad reference raises PatchError with the index of the failing op, so the repair loop can tell the model which op to fix. Whether the result is a sensible workflow is left to the validator.

3.3 Validator (validator.py)

Errors block a proposal from reaching the canvas; warnings are legal BPMN that probably isn't what the author meant, shown in Review mode. Every issue names the node and flow ids involved so the SPA can highlight them. Codes are stable: the repair loop sends them back to the model.

CodeSeverityRule
AD001errorDuplicate id (ids are shared by nodes and flows in BPMN XML)
AD002errorFlow points to a node that doesn't exist
AD003errorFlow loops from a node to itself
AD004errorNo start event
AD005errorMore than one start event
AD006errorNo end event
AD007errorStart event has incoming flows
AD008errorEnd event has outgoing flows
AD009errorNode can never be reached from the start event
AD010errorNode has no path to an end event (an instance there would be stuck)
AD011errorExclusive or inclusive gateway has two or more branches without a condition (one fallback branch is allowed)
AD012warningConditions on flows out of a parallel gateway (Flowable ignores them)
AD013warningA non-gateway node has several outgoing flows (an implicit parallel split; usually a missing gateway)
AD014errorA field set on a node type it does nothing for, e.g. assignee on a service task
AD015warningActivity without a label
AD016warningTwo or more flows between the same pair of nodes
AD017warningUser task with no assignee and no candidate groups (added in A3)

A flow that fails AD002 or AD003 is left out of the reachability checks, so one bad flow produces one issue instead of a cascade.

3.4 Canvas conversion (canvas.py)

  • to_canvas produces the SPA's GraphSnapshot shape, the same one parseBpmnXml returns: nodes with type, position and data; edges of type smoothstep with data.conditionExpression. Every node gets position (0, 0) so the SPA's needsAutoLayout triggers layout.
  • from_canvas reads the current canvas so the agent can edit or review it, ignoring position, size and selection. A node type the agent can't author raises an error instead of being dropped, because dropping it would make an Edit silently delete it.

3.5 Tests

uv run pytest in services/agentic-designer/: 51 tests. One fully valid "loan approval" process has no issues at all; each malformed fixture changes it in exactly one way and must produce exactly its one error code, no more and no fewer. The suite was checked against three deliberately introduced bugs (a relaxed gateway rule, a disabled dead-end check, and remove_node leaving flows behind), and each made tests fail.

4. Service Internals

  • Routes: POST /generate, POST /edit, POST /review, streaming progress and the final proposal as server-sent events. The gateway exposes them as /api/agent/generate and so on.
  • Auth: verifies the Supabase JWT against JWKS, the same as workflow-runtime, and reads the tenant id and app_metadata.role. Only designer and tenant_admin can generate and edit.
  • LLM layer: as built, LLMProvider.generate_json(system, turns, schema) -> JSON text (Section 4a); Gemini first, Anthropic later. A thin interface over the two SDKs rather than a large framework, because tool-calling behavior differs between providers and the repair loop needs to see the raw calls.
  • Cost and safety: per-tenant rate limits in the service plus per-IP limits at nginx; a token cap per request; workflow names, descriptions and imported XML are treated as untrusted data in prompts, never as instructions; API keys live only in this service's environment.

Flow

  1. In the Designer, a BPMN workflow is open and the user (designer or tenant_admin) clicks Generate with AI. The side panel replaces the properties panel.
  2. The SPA POSTs {"description": ...} (10 to 4,000 characters) to /api/agent/generate with the Supabase JWT, via apiStream in Designer/src/lib/apiClient.ts. It reads the response stream with fetch, because EventSource can't send an Authorization header.
  3. The service checks the JWT, the role and the per-tenant rate limit before any model call, so a refused request costs nothing.
  4. The generate loop (generate.py) asks the model for a graph, parses it, validates it, and on errors sends the codes and ids back, at most 2 repairs (3 model calls in total).
  5. On success the SPA lays the graph out with the existing applyAutoLayout and replaces the canvas, marked as unsaved. It asks first if the canvas isn't empty. Undo restores the previous canvas. Nothing is saved until the user clicks Save Version.

Streamed events

EventDataMeaning
attemptattemptA model call is starting
invalidattempt, issuesThat proposal was rejected; the codes are being sent back
resultattempt, graph (canvas shape), issues (warnings only)Accepted
failedattempt, issuesStill invalid after the repair budget; no graph
errormessageThe provider call failed; the message is safe to show (e.g. quota reached)

Schema failures (output that isn't a WorkflowGraph at all) use code AD000; the validator's codes start at AD001.

Decisions made while building

  • One OpenAI-compatible adapter for NVIDIA and OpenRouter. OpenAICompatibleProvider uses response_format of type json_schema with the same schema, and strips a markdown code fence if a model adds one anyway. Adding another OpenAI-compatible host is a line in PROVIDERS (app.py).
  • Structured output instead of tool calls for Gemini. The LLM interface is one method, generate_json(system, turns, schema). Gemini implements it with response_json_schema, which takes the full Pydantic JSON Schema. An Anthropic adapter would implement the same method with a forced tool call. Feedback on a rejected proposal goes back as plain conversation turns, so no provider-specific tool-result plumbing is needed.
  • The description is fenced as data. It is wrapped in <description> tags, and the system prompt says to ignore instructions inside it. This reduces prompt injection; it does not eliminate it, and the validator plus human approval remain the real controls.
  • Every model call is metered (tokens, estimated cost, outcome, tenant, request id) for the API spend tracker; see SpendTracker.html Section 3a.
  • Only sizes and outcomes are logged (tenant, user, description length, attempts, duration), never the description itself.
  • Provider errors become plain messages. A 429 becomes "rate limit or quota reached"; other failures become a short message. Provider internals stay in the server log.

They cover the repair loop (the second model call must contain the rejected proposal and the specific error codes and ids), giving up after exactly 3 calls, schema errors, warnings riding along with a result, the fenced description, and the HTTP layer: 401 for missing, forged or expired tokens; 403 for viewer, approver or no tenant; 422 for description length; 429 per tenant; 503 without a provider; provider failures becoming error events without leaking details. 4b. Edit Mode as Built (Phase A2)

Built September 27, 2026: POST /edit (edit.py) and the Edit tab of the Designer panel (toolbar button renamed AI Designer; AgentPanel.tsx, lib/editPreview.ts).

Flow

  1. With a BPMN workflow open, the user picks the Edit tab (the default when the canvas has nodes) and describes a change (5 to 2,000 characters).
  2. The SPA sends the instruction and the canvas as it is. The service converts the canvas with from_canvas; an unsupported element (e.g. a boundary event), an empty canvas, or more than 300 nodes is refused with 422 before any model call.
  3. The model gets the current graph and the instruction, both fenced as data, and returns patch operations (A0's add_node, update_node, remove_node, connect, disconnect, set_condition), never a replacement graph.
  4. Code applies them and validates the result. An edit is rejected only for errors it introduces: problems the workflow already had are reported as "already in this workflow (not caused by this edit)" and don't block it. A bad reference is sent back naming the failing op's index; an edit that changes nothing is sent back too. At most 2 repairs.
  5. The SPA previews the result on the canvas without disturbing the layout: existing nodes keep their position and any Designer-only data; new nodes are placed next to the node they connect from, clear of existing nodes. Added nodes and flows are outlined green, changed ones yellow, and the panel lists every change in words, including removals (which can't be shown on the canvas).
  6. Accept keeps the changes (unsaved; highlights removed). Reject restores the canvas exactly, including its unsaved-changes state. Nothing is saved until Save Version, so approvals apply as before.

Hardening that came out of the live runs

  • Empty replies are retried in both Generate and Edit, with the same conversation and within the repair budget, instead of failing the request (AD000: "The model returned an empty reply; retrying").
  • Keepalive: while a model works, the stream sends an SSE comment every 15 seconds so the browser and proxies don't time out; the SPA's stream reader skips them.
  • Timeouts: the OpenAI-compatible client waits up to 300 seconds and no longer retries by itself. An SDK retry after a timeout had doubled one live edit to ten minutes; the generate/edit loops own retrying.
  • The /generate and /edit endpoints share one code path for refusals, metering and streaming. Edit calls are metered as their own feature (edit) in the spend tracker.

Verified

  • 108 agent tests (16 new): ops, graph and diff returned; graph and instruction fenced as data; failing op index sent back; edits that break the process rejected (exactly AD009 + AD010 when a merge gateway is removed without rewiring); pre-existing problems don't block; no-op edits refused; the original graph untouched; empty replies retried and budgeted; keepalive; edit-model selection; HTTP streaming, metering, 422 refusals before any model call, and role checks. Three deliberately introduced bugs were each caught.
  • UI, with Playwright against the running app (stand-in login, mocked database rows, a real edit payload): the preview highlights 2 new nodes and 4 flows on the canvas, the panel lists all 7 changes, Reject restores the canvas to its 7 original nodes with no highlights left, and there were no console errors.
  • Not yet verified: the browser flow by a real logged-in user against the live model.

4c. Review Mode as Built (Phase A3)

Built September 27, 2026: POST /review (review.py) and the Review tab of the AI Designer panel. Read-only: nothing it returns is applied to the workflow.

Two kinds of finding, kept apart

  • Check (code): the validator’s rules AD001–AD017. They need no model, arrive first (before the model answers), and are still returned when no model is configured or the model fails. New rule AD017 (warning): a user task with no assignee and no candidate groups, which lands in nobody’s task list. Generate and Edit prompts now ask for an assignment on every user task.
  • AI (judgement): only what code can’t decide, in fixed categories: missing_path, incomplete_conditions, overlapping_conditions, unclear_label, assignment, ordering, other; severity warning or suggestion. The model is told what the checks already found so it doesn’t repeat them, and an optional focus (“Is every approval path complete?”, up to 500 characters) steers it. All of it is fenced as data.
  • Code checks what the model says: node and flow ids that don’t exist are dropped; a finding that pointed only at invented ids is discarded; at most 10 AI findings. Up to 3 attempts (empty or malformed replies are retried); if none works, the checks are returned with “AI review unavailable”.

In the panel

Findings are grouped as Problems, Warnings and Suggestions, each labelled Check or AI with its code. Clicking one selects its nodes and flows on the canvas (selection only; the workflow isn’t changed).

Seeded-defect evaluation (A3’s completion criterion)

tests/review_samples.py plants one defect per sample in the loan process; scripts/review_eval.py runs them all against the configured model and reports which were caught. It is the first piece of A5’s evaluation harness (superseded in A5 by scripts/eval.py, Section 4e).

Three deliberately introduced bugs were each caught.
  • UI with Playwright against the running app: Review shows the check and AI findings grouped and labelled, and clicking a finding selects exactly its nodes; no console errors.
  • Found, not fixed (pre-existing): opening a saved workflow immediately shows “Unsaved changes”, because the canvas store marks the workflow dirty on every React Flow change, including the size measurements React Flow reports on first render. Separate from this work; worth fixing in the Designer.

4d. CMMN and DMN as Built (Phase A4)

Built September 27, 2026. Generate, Edit and Review now work for all three notations the Designer edits. They are written once against a Spec per notation (specs.py: model, validator, conversion, prompts); requests carry spec: BPMN (default), CMMN or DMN.

Contracts, matched to the Designer’s adapters

  • CMMN (cmmn.py), mirroring cmmnAdapter.ts: a flat case of plan items (cmmnHumanTask, cmmnTask, cmmnMilestone, cmmnStage) and cmmnSentry gates, linked by onPart (item → sentry, on a standard event), entry and exit (sentry → item). Sentries may have an if-condition; human tasks may be blocking.
  • DMN (dmn.py), mirroring dmnAdapter.ts: standalone decision tables with a hit policy (and aggregation for COLLECT), typed inputs and outputs, and rules of FEEL entries. Conventions from the Designer’s sample: quoted strings, - for any value.
  • Anchored on real files: the Designer’s own samples, parsed by its own adapters (tests/data): the investigation case (17 nodes, 19 links) and the investigation decisions (COLLECT/SUM, PRIORITY, UNIQUE). Both convert with zero validator issues and round-trip exactly, DMN table ids included, so drift between these contracts and the adapters fails a test.

Edit: the complete updated model, diffed by code

For CMMN and DMN the model returns the whole updated model rather than BPMN’s patch operations: patch ops are shaped around BPMN nodes, and a decision table is a grid where “here is the updated table” is the natural unit. Code still computes the diff (nodes and links for CMMN; decisions and rules for DMN), so the review-before-accept step is unchanged, and an edit is still rejected only for errors it introduces. Edits keep the DMN file’s identity and decision-table ids.

In the Designer

  • The AI Designer button now appears for all three notations.
  • CMMN works on the canvas like BPMN: generated cases are laid out automatically; edits are previewed with highlights (links described by their kind and event, e.g. “(on complete)”, “(entry)”).
  • DMN has no canvas. Generate replaces the decision tables (keeping or deriving the file’s DMN id and namespace). Edit lists the proposed changes (“added rule 5”, “changed rule 2”) and applies nothing until Accept, so Reject has nothing to undo. Review findings open the decision they concern. Applying a result marks the workflow as having unsaved changes (the store’s setDmnModel doesn’t do that by itself).

4e. Evaluation and Grounding as Built (Phase A5)

Evaluation harness

scripts/eval.py run --provider … --model … runs every case through the real Generate, Edit and Review loops (metered like production) and writes a JSON report to evals/reports/; scripts/eval.py compare puts reports side by side. It supersedes A3’s review_eval.py.

  • 22 cases across all three modes and notations: 7 Generate, 4 Edit, 9 Review (6 seeded BPMN defects, plus real defects in the Designer’s DMN and CMMN samples), and a grounding pair.
  • Checks judge what a process owner cares about, not exact shapes: the steps, conditions and gates the request implies (who does a step counts as much as its label); for Edit, that the asked-for change is there and nothing else was lost.
  • DMN is judged by execution: a small FEEL evaluator (evaluation/feel.py: literals, comparisons, ranges, lists, not(), every hit policy) runs the generated table on test inputs and compares the answers. Checked against the Designer’s sample, where it also confirmed the gap Review reported in A4 (department “HR” with 1 incident matches no rule).
  • Honest scoring: a case with no valid result, or a provider error, fails every one of its checks (never “0/0”); a check that crashes fails itself without stopping the run; unpriced calls leave cost unknown, never $0; “no answer” (every attempt empty) is counted separately from a wrong answer.

Grounding in the tenant’s own workflows

  • What it does: before Generate and Edit, the agent finds the tenant’s most similar existing workflows (same notation, current versions, not archived, never the open workflow itself) and shows the model condensed summaries of them, fenced as data, with an instruction to follow their conventions (group and assignee names, condition variables, delegate expressions, labelling style) where they fit. The stream’s first event, grounding, names the workflows used, and the Designer panel shows them (“Following the conventions of your workflow ‘Mortgage approval’”).
  • Storage (decided with the product owner): pgvector in the Supabase design-time database, table workflow_embeddings and search function match_workflow_embeddings (DataArchitecture.html Section 3.10). The agent reads and writes them through PostgREST as the logged-in user; there is no service key in the agent, so RLS keeps tenants apart. Verified on the live database with synthetic rows (rolled back): tenant A sees only its own rows and search results; anonymous access is refused.
  • Embeddings: configurable (AGENT_EMBED_PROVIDER); NVIDIA nvidia/nemotron-3-embed-1b now (2048 dimensions; chosen over the other callable NVIDIA model for speed and clearer separation), Gemini gemini-embedding-001 once its cap allows. The column has no fixed dimension and searches filter by model, so switching re-embeds rather than breaking. Several listed NVIDIA embedding models return 404.
  • Written lazily: when grounding runs, current versions without an embedding for the configured model are summarized, embedded and upserted (at most 20 per request). Embedding calls are metered in the spend tracker as feature embed.
  • Best-effort: any grounding failure (Supabase, embeddings, rate limits) means no examples, never a failed request. Matches below similarity 0.25 are ignored.

6. Risks & Open Questions

  • Structurally valid is not the same as correct. The validator catches broken graphs, not wrong business logic. The approval flow remains the control for that.
  • Data leaves the environment. Workflow content is sent to an external LLM provider. That may need a data-handling review before real tenant data is used.
  • The canvas contract is mirrored, not shared. canvas.py copies the shape of the SPA's GraphSnapshot in Python. If the SPA's node data changes, this has to change with it. A1's end-to-end test (generate → canvas → save) is what will catch drift.
  • Provider differences. Tool-calling reliability varies by provider and model; A5's eval harness is what makes that measurable instead of anecdotal.
