0. Decision Summary

CWP.html listed the Agentic Designer as out of scope until Designer's editors matured. They have: BPMN, CMMN and DMN editing, versioning, approvals and one-click Publish all exist. This document is the design for adding an AI authoring assistant on top of them without weakening any of the governance already built.

What's Decided
  • A separate Python / FastAPI service, agentic-designer, reached through the nginx edge gateway (Services.html).
  • Provider-agnostic LLM layer. A thin LLMProvider interface with Anthropic and Gemini adapters to start; provider and model come from configuration.
  • The model never writes BPMN XML and never writes to the database. It proposes changes against a typed graph contract; code validates them; the SPA applies them to the canvas; the user saves through the existing path.
  • Agent output is always a draft. It goes through the same RLS, versioning, approval and audit flow as hand-made changes.
  • Stateless in v1. The client sends the conversation and the current graph with each request.

2. The Core Rule: The Model Proposes, Code Decides

  1. The model returns tool calls against the typed graph contract (Section 3): a whole graph for Generate, patch operations for Edit.
  2. The service validates the proposal: schema first (Pydantic), then structure (the validator rules in Section 3).
  3. If validation fails, the errors go back to the model for at most 2 repair rounds; after that the user sees the errors instead of a broken graph.
  4. The SPA converts the accepted graph into its canvas format (GraphSnapshot in Designer/src/data/workflows.ts). Every node arrives at position (0, 0), which makes the existing needsAutoLayout / applyAutoLayout (Designer/src/adapters/autoLayout.ts) lay it out. The existing BPMN adapter produces the XML on save.
  5. Saving uses the existing path, so tenant isolation, workflow_versions, approvals and audit_logs all apply unchanged.

3. Graph Contract

Built in phase A0 at services/agentic-designer/src/agentic_designer/. No LLM and no HTTP yet: this is the contract every later phase is checked against.

3.1 Graph (graph.py)

WorkflowGraph holds nodes and edges. JSON field names are camelCase so they match the SPA's NodeData exactly. Unknown fields are rejected rather than dropped, so a model inventing an attribute is caught.

ElementFieldsNotes
Nodeid, type, label, documentation, assignee, candidateGroups, delegateExpression, formKeyid must be a valid BPMN id (^[A-Za-z_][A-Za-z0-9_.-]*$)
Edgeid, source, target, label, conditionExpressionNo separate "default flow" flag: the Designer's BPMN adapter doesn't write one, so one unconditioned branch acts as the fallback

Node types: the Designer's BPMN palette (startEvent, endEvent, intermediateEvent, userTask, serviceTask, businessRuleTask, callActivity, subProcess, exclusiveGateway, parallelGateway, inclusiveGateway) minus boundaryEvent (needs a host node the canvas format can't express yet) and genericNode (the Designer's fallback for unknown elements). CMMN and DMN come in A4.

Field applicability: assignee and candidateGroups on user tasks; formKey on user tasks and start events; delegateExpression on service tasks. These match what Flowable acts on.

3.2 Patch operations (patch.py)

OpPayloadNotes
add_nodenode
update_nodeid, changesLabel and the optional fields only. Changing id or type is not allowed: that's a remove plus an add, so the node's flows get reconsidered
remove_nodeidAlso removes every flow touching the node
connectedgeBoth ends must exist
disconnectedgeId
set_conditionedgeId, conditionExpressionnull clears it

apply_patch returns a new graph and never modifies the original (so Reject restores exactly what was on the canvas). A bad reference raises PatchError with the index of the failing op, so the repair loop can tell the model which op to fix. Whether the result is a sensible workflow is left to the validator.

3.3 Validator (validator.py)

Errors block a proposal from reaching the canvas; warnings are legal BPMN that probably isn't what the author meant, shown in Review mode. Every issue names the node and flow ids involved so the SPA can highlight them. Codes are stable: the repair loop sends them back to the model.

CodeSeverityRule
AD001errorDuplicate id (ids are shared by nodes and flows in BPMN XML)
AD002errorFlow points to a node that doesn't exist
AD003errorFlow loops from a node to itself
AD004errorNo start event
AD005errorMore than one start event
AD006errorNo end event
AD007errorStart event has incoming flows
AD008errorEnd event has outgoing flows
AD009errorNode can never be reached from the start event
AD010errorNode has no path to an end event (an instance there would be stuck)
AD011errorExclusive or inclusive gateway has two or more branches without a condition (one fallback branch is allowed)
AD012warningConditions on flows out of a parallel gateway (Flowable ignores them)
AD013warningA non-gateway node has several outgoing flows (an implicit parallel split; usually a missing gateway)
AD014errorA field set on a node type it does nothing for, e.g. assignee on a service task
AD015warningActivity without a label
AD016warningTwo or more flows between the same pair of nodes

A flow that fails AD002 or AD003 is left out of the reachability checks, so one bad flow produces one issue instead of a cascade.

3.4 Canvas conversion (canvas.py)

  • to_canvas produces the SPA's GraphSnapshot shape, the same one parseBpmnXml returns: nodes with type, position and data; edges of type smoothstep with data.conditionExpression. Every node gets position (0, 0) so the SPA's needsAutoLayout triggers layout.
  • from_canvas reads the current canvas so the agent can edit or review it, ignoring position, size and selection. A node type the agent can't author raises an error instead of being dropped, because dropping it would make an Edit silently delete it.

3.5 Tests

uv run pytest in services/agentic-designer/: 51 tests. One fully valid "loan approval" process has no issues at all; each malformed fixture changes it in exactly one way and must produce exactly its one error code, no more and no fewer. The suite was checked against three deliberately introduced bugs (a relaxed gateway rule, a disabled dead-end check, and remove_node leaving flows behind), and each made tests fail.

4. Service Internals

  • Routes: POST /generate, POST /edit, POST /review, streaming progress and the final proposal as server-sent events. The gateway exposes them as /api/agent/generate and so on.
  • Auth: verifies the Supabase JWT against JWKS, the same as workflow-runtime, and reads the tenant id and app_metadata.role. Only designer and tenant_admin can generate and edit.
  • LLM layer: as built, LLMProvider.generate_json(system, turns, schema) -> JSON text (Section 4a); Gemini first, Anthropic later. A thin interface over the two SDKs rather than a large framework, because tool-calling behavior differs between providers and the repair loop needs to see the raw calls.
  • Cost and safety: per-tenant rate limits in the service plus per-IP limits at nginx; a token cap per request; workflow names, descriptions and imported XML are treated as untrusted data in prompts, never as instructions; API keys live only in this service's environment.

Flow

  1. In the Designer, a BPMN workflow is open and the user (designer or tenant_admin) clicks Generate with AI. The side panel replaces the properties panel.
  2. The SPA POSTs {"description": ...} (10 to 4,000 characters) to /api/agent/generate with the Supabase JWT, via apiStream in Designer/src/lib/apiClient.ts. It reads the response stream with fetch, because EventSource can't send an Authorization header.
  3. The service checks the JWT, the role and the per-tenant rate limit before any model call, so a refused request costs nothing.
  4. The generate loop (generate.py) asks the model for a graph, parses it, validates it, and on errors sends the codes and ids back, at most 2 repairs (3 model calls in total).
  5. On success the SPA lays the graph out with the existing applyAutoLayout and replaces the canvas, marked as unsaved. It asks first if the canvas isn't empty. Undo restores the previous canvas. Nothing is saved until the user clicks Save Version.

Streamed events

EventDataMeaning
attemptattemptA model call is starting
invalidattempt, issuesThat proposal was rejected; the codes are being sent back
resultattempt, graph (canvas shape), issues (warnings only)Accepted
failedattempt, issuesStill invalid after the repair budget; no graph
errormessageThe provider call failed; the message is safe to show (e.g. quota reached)

Schema failures (output that isn't a WorkflowGraph at all) use code AD000; the validator's codes start at AD001.

Decisions made while building

  • One OpenAI-compatible adapter for NVIDIA and OpenRouter. OpenAICompatibleProvider uses response_format of type json_schema with the same schema, and strips a markdown code fence if a model adds one anyway. Adding another OpenAI-compatible host is a line in PROVIDERS (app.py).
  • Structured output instead of tool calls for Gemini. The LLM interface is one method, generate_json(system, turns, schema). Gemini implements it with response_json_schema, which takes the full Pydantic JSON Schema. An Anthropic adapter would implement the same method with a forced tool call. Feedback on a rejected proposal goes back as plain conversation turns, so no provider-specific tool-result plumbing is needed.
  • The description is fenced as data. It is wrapped in <description> tags, and the system prompt says to ignore instructions inside it. This reduces prompt injection; it does not eliminate it, and the validator plus human approval remain the real controls.
  • Only sizes and outcomes are logged (tenant, user, description length, attempts, duration), never the description itself.
  • Provider errors become plain messages. A 429 becomes "rate limit or quota reached"; other failures become a short message. Provider internals stay in the server log.

Tests

74 tests (uv run pytest), using a scripted provider so they cost nothing. They cover the repair loop (the second model call must contain the rejected proposal and the specific error codes and ids), giving up after exactly 3 calls, schema errors, warnings riding along with a result, the fenced description, and the HTTP layer: 401 for missing, forged or expired tokens; 403 for viewer, approver or no tenant; 422 for description length; 429 per tenant; 503 without a provider; provider failures becoming error events without leaking details. Two deliberately introduced bugs were each caught: dropping the feedback to the model, and disabling the role check.

6. Risks & Open Questions

  • Structurally valid is not the same as correct. The validator catches broken graphs, not wrong business logic. The approval flow remains the control for that.
  • Data leaves the environment. Workflow content is sent to an external LLM provider. That may need a data-handling review before real tenant data is used.
  • The canvas contract is mirrored, not shared. canvas.py copies the shape of the SPA's GraphSnapshot in Python. If the SPA's node data changes, this has to change with it. A1's end-to-end test (generate → canvas → save) is what will catch drift.
  • Provider differences. Tool-calling reliability varies by provider and model; A5's eval harness is what makes that measurable instead of anecdotal.
