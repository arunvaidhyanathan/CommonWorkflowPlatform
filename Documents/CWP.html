0. Why This Document Exists

Designer.html was the right source of truth while the Designer sub-app was the only thing being built. It no longer is. The platform now spans an app shell, a Designer (built), an Onboarding flow (design phase), a Workbench (design phase), and a Governance model (built, with real gaps identified for a next iteration) -- plus two explicitly deferred components. Calling the whole thing "Designer" stopped being accurate. Common Workflow Platform (CWP) is the umbrella name for everything; this document is the map, not a replacement for the detailed component docs it links to.

Document Set Rationale

One file per component instead of one ever-growing file, specifically so a new session only has to load the doc relevant to what it's working on, rather than the entire platform's history. This index is what makes that navigable rather than fragmented.

2. Cross-Cutting Architecture

What every component shares, so this doesn't need re-explaining in each component doc:

  • Single PostgreSQL database, with row-level security as the tenant isolation boundary -- every table is scoped by tenant_id, checked against current_tenant_id(), which reads the caller's JWT app_metadata.tenant_id claim.
  • One Vite + React 19 + TypeScript SPA at WaaS/Designer -- despite the folder name, this is now the CWP application shell; component screens are routes within it, not separate apps. (Renaming the folder is a future housekeeping item, not urgent.)
  • Shared role claim, app_metadata.role, read via current_role_claim() in every RLS policy. Governance.html proposes evolving this from three flat values to a richer model; whatever that becomes, it stays the single mechanism every component's authorization checks against.
  • Privileged writes go through serverless functions, never a direct client write with elevated permission -- established with admin-set-role, and the pattern every future privileged operation (tenant creation, invites) should follow.
  • Shared visual theme -- the Citi light-blue design tokens (--citi-blue-dark, --citi-blue, etc.) are currently duplicated as inline Tailwind/CSS across the app and across each of these HTML docs. Worth extracting into one shared source eventually; not urgent while the component count is still small.
  • Services behind one edge gateway, as of September 27, 2026 -- a standalone nginx gateway is the only public entry point: it serves the SPA and routes /api/* to CWP's own services (workflow-runtime, and agentic-designer once built). Supabase stays the identity and design-time data backend. Every service verifies the Supabase JWT itself. Local development runs the whole stack with docker compose up. The "Runtime Gateway" name in the bullet below is retired; that service is now workflow-runtime. See Services.html.
  • Two backends, not one, as of August 3, 2026 -- the PostgreSQL database remains the single source of truth for identity, tenancy, RLS, and all design-time data (unchanged). A second, additive backend, the Java 21 / Spring Boot 4 Runtime Gateway (WorkflowWrapper.html), owns everything workflow-runtime-shaped (deployments, historic instances, CMMN plan-item state). It connects to the same Postgres database via a new runtime schema over direct JDBC, not through the REST-over-Postgres layer/RLS -- it's a privileged component like a serverless function, not a browser client, and is responsible for its own tenant scoping in application code. A real Flowable 8.0.0 engine is embedded in-process (Process/CMMN/DMN) -- an earlier version of this document believed Flowable didn't run on Spring Boot 4, which was true when first checked but was five months stale by the time it mattered; see WorkflowWrapper.html Section 4 for the correction. Form rendering is the one piece still unbuilt: Flowable's standalone Form Engine is deprecated, and the replacement needs its own design pass.
